3. 立体报告：数据告诉我们 BudgetFlow 什么时候能赢

这部分的核心是把不同数据状态分清楚：BudgetFlow 赢在 mixed batch；strong-only 赢在强模型本身已经覆盖 batch 的情况；learned router 在模型选择信号足够准、Task Value 不是主要差异时会贴近 frontier。

例子 1：mixed batch regime 一个 batch 里有高价值任务、普通任务和很难救的任务；强模型只对其中一部分任务有明显收益，便宜模型也能解决一部分任务。此时 BudgetFlow 的动作是把 strong-model opportunity 留给高价值且强模型有增益的任务。latest run 对应这个状态：BudgetFlow 16/30、TRV 18.00、TRV/$ 1.81，领先 best control 的 15/30、17.00、1.71。
例子 2：strong-model regime 一个 batch 里强模型对大多数可解决任务都有效，而且 $9.95 共享预算足够支撑强模型覆盖主要任务。此时 strong-only 就是很强的 frontier point。strong boundary run 对应这个状态：strong-only 17/30、TRV 20.00、TRV/$ 2.01，领先 BudgetFlow 的 15/30、17.50、1.76。
例子 3：learned-router regime 一个 batch 里“哪个模型更适合这个任务”本身就是主要信号，Task Value 排序带来的额外收益较小。此时 learned router 会很接近甚至领先 frontier。一个 diagnostic audit 中，learned router 达到 19/30、TRV 21.00、TRV/$ 2.11，高于 BudgetFlow 的 14/30、15.00、1.51。

Why this helps the paper

这不是把 learned router 当成附属 baseline，而是把它放进同一个 frontier 报告框架。

三种状态一起构成论文价值：BudgetFlow 说明 value-aware allocation 什么时候创造价值；strong-only 说明强模型什么时候已经形成边界；learned router 说明 per-task model fit 什么时候已经足够强。

所以结论不是随机输赢。BudgetFlow 能赢的具体条件是 mixed batch：任务价值差异明显，强模型只对部分任务值得花钱，便宜模型也有可用机会。

数据支撑这个条件：latest run 的可比较任务中，cheap-model-favorable pass 有 6 个，strong-model-favorable pass 有 5 个，both-fail 有 7 个。这个结构给了 BudgetFlow 分配空间。

strong-only 赢在两轮：strong boundary 和 near-boundary。它们的共同特征是 strong-only 同时拿到更高 resolved count、更高 TRV 和更高 TRV/$；这说明那两批任务中强模型整体覆盖有效，预算也没有把 strong-only 压垮。

learned router 赢或接近 frontier 的条件也清楚：它的 value-blind model-fit signal 足够准，或者 cost / token consumption 因 KV cache 折扣变得很低。此时 Task Value 带来的额外治理收益会变小；当高价值任务需要被优先保护时，BudgetFlow 的优势重新变大。

4. BudgetFlow 的路由公式，用白话讲就是四个问题

论文里的公式不是为了制造复杂感。它表达的是一个非常直接的判断：把下一次稀缺的模型机会给哪个任务，值不值。

每个任务先回答四个问题

  • Value这个任务如果解决了，价值有多高？高价值任务值得更多预算关注。
  • Cost / Token这个任务预计会消耗多少 cost / token？高消耗任务需要提前规划 cap。
  • Fit强模型相对便宜模型是否真的更有帮助？只有有明显收益时，强模型机会才更值。
  • Budget当前 batch 还剩多少钱？给当前任务多花一点，就会影响后面任务。
直观路由分数：值得花钱的程度 ≈ 任务价值 × 强模型增益 ÷ 预计 cost / token consumption，并且必须通过剩余 batch 预算检查。
给 strong model 高价值任务，强模型收益明显，预计 cost / token consumption 可控，batch 预算还允许。
给 cheap model 任务价值正常，便宜模型已经有足够机会，强模型增益不明显。
stop / defer 继续花钱的预期价值低，或者剩余预算更应该留给后续任务。

一个直观例子：任务 A 价值 2.5，强模型历史上对这类任务更有效，预计 cost / token consumption 可控，BudgetFlow 会倾向于给它 strong-model opportunity。

任务 B 价值 1.0，便宜模型已经能解决类似任务，强模型增益很小，BudgetFlow 会倾向于用 cheap model，把强模型机会留给更需要的任务。

任务 C 两个模型都很可能失败，而且预计很耗预算，BudgetFlow 会倾向于少投入或停止，把共享预算保护下来。

5. 这篇论文最值得讲清楚的价值

BudgetFlow 把 agent 系统从“单个请求怎么选模型”推进到“一个任务 batch 怎么共享预算”。

数据说明任务之间确实有差异：有些任务便宜模型更划算，有些任务强模型更划算，还有些任务两个模型都失败。

因此我们需要的不只是一个 router，而是一个能同时看任务价值、模型收益、预计 cost / token consumption 和剩余预算的 budget governance framework。

SWE-bench 是严格 verifier 的实例；同一套接口也可以迁移到客服、文档、表格、科研任务等有验收信号的 agent workload。
