BudgetFlow: 把 agent 批量任务变成可解释的预算治理问题

这篇论文的核心贡献有三点：形式化 shared hard budget 下的 batch-level value allocation，给出跨任务可迁移的 BudgetFlow interface，并用 frontier mode 解释当前 batch 由哪种机制决定 cost-value frontier。

16 / 30 latest 5-policy run 中 BudgetFlow 解决任务数最高。
TRV 18.00 同样预算下，BudgetFlow 解决的任务价值最高。
1.81 TRV/$ BudgetFlow 在 latest run 中价值效率最高。

贡献 1：Batch-Level Value Allocation Problem。给定一批任务、一个 shared hard budget、多个 model tiers 和 verifier outcomes，BudgetFlow 的目标是在固定预算内最大化 verifier-confirmed Total Resolved Value，同时报告 resolved rate 和 TRV per dollar。

贡献 2：Generalizable BudgetFlow Interface。每个任务通过 Task Value、Estimated Token Cost、model-fit prior、verifier 和 Shared Budget 进入同一套 allocation rule。coding、marketing、PPT、support、research 是任务来源，不是 strong model access 的决策特征。

贡献 3：Frontier Mode Analysis。多轮 30-task evidence 显示 frontier 由三类机制主导：Value Divergence、Strong Coverage、Model Fit。这个分析解释为什么不同 policy 会形成边界，并指出 BudgetFlow 应吸收哪个信号。

3. 立体报告：frontier mode、机制和操作条件

这部分回答一个问题：同一套 shared budget 下，当前 batch 由哪个机制决定 frontier。数据给出三类 operating condition：Value Divergence、Strong Coverage、Model Fit。

1. BudgetFlow 推动 frontier：Value Divergence Mode 条件：任务价值差异大，T2 和 T3 都有可用机会，强模型收益集中在部分任务。机制：BudgetFlow 把 shared budget 放到高价值、且有模型收益空间的任务上。4-policy value case 里，BudgetFlow 少解 1 个任务，但 TRV 和 TRV/$ 都更高；高价值任务（Task Value ≥ 1.5）上解出 5 个、价值 9.50，pure strong 解出 4 个、价值 7.00。

具体任务证据：相对 strong-only，BudgetFlow-only 解决了 pallets__flask-4992（2.50）和 sympy__sympy-17655（1.00），而 strong-only-only 的 3 个任务各为 1.00。相对 learned router，BudgetFlow-only value 是 6.50，route-only value 是 3.00。可泛化结论：当任务价值差异真实存在，frontier 由 Value Divergence 决定。
2. strong-only 形成边界：Strong Coverage Mode 条件：强模型能在 shared budget 内覆盖整批任务，并且能补上尾部 T3-resolvable tasks。机制：strong-only 用完整覆盖换取 tail completion；BudgetFlow 在部分任务上节省预算，但错过了更多 T3-only tail value。strong boundary run 里 strong-only 覆盖 30/30、17 个 trusted pass；BudgetFlow 是 25 个 paid attempts、15 个 pass。

直观讲：BudgetFlow 的价值来自 value-aware batch governance；strong-only 的优势来自 full-batch strong coverage；learned router 的优势来自准确 model-fit signal。

当 strong-only 或 learned router 成为边界时，结果暴露的是当前 routing policy 对 coverage 或 model-fit signal 的权重不足。真实系统可以先跑少量 batch，识别 frontier mode，再更新 routing policy。

latest positive run 说明这些信号可以被统一起来：BudgetFlow 16/30、TRV 18.00、TRV/$ 1.81，高于 learned router 的 15/30、17.00、1.71，也高于 strong-only 的 15/30、16.50、1.66。那一轮 BudgetFlow-only 是 django__django-15814 和 django__django-12908，Route-only 是 sympy__sympy-17655。

因此论文报告的不是单一排行榜，而是 frontier mode：在什么条件下 Value Divergence、Strong Coverage、Model Fit 分别决定 frontier。这个报告方式可以迁移到客服、文档、表格、科研任务等有 Task Value、Estimated Token Cost、model-fit prior 和 verifier 的 agent workload。

4. BudgetFlow 的路由公式，用白话讲就是四个问题

论文里的公式表达的是一个直接判断：在当前 shared budget 下，把下一次稀缺的 strong-model opportunity 给哪个任务，值不值。

每个任务先回答四个问题

  • Value这个任务如果解决了，价值有多高？高价值任务值得更多预算关注。
  • Token Cost这个任务预计会消耗多少 token 成本？高消耗任务需要提前规划 cap。
  • Fit强模型相对便宜模型是否真的更有帮助？只有有明显收益时，强模型机会才更值。
  • Budget当前 batch 还剩多少钱？给当前任务多花一点，就会影响后面任务。
直观路由分数：值得花钱的程度 ≈ 任务价值 × 强模型增益 ÷ 预计 token 成本，并且必须通过 Shared Budget 检查。
给 strong model 高价值任务，强模型收益明显，预计 token 成本可控，Shared Budget 还允许。
给 cheap model 任务价值正常，便宜模型已经有足够机会，强模型增益不明显。
stop / defer 继续花钱的预期价值低，或者剩余预算更应该留给后续任务。

一个直观例子：任务 A 价值 2.5，强模型历史上对这类任务更有效，预计 token 成本可控，BudgetFlow 会倾向于给它 strong-model opportunity。

任务 B 价值 1.0，便宜模型已经能解决类似任务，强模型增益很小，BudgetFlow 会倾向于用 cheap model，把强模型机会留给更需要的任务。

任务 C 两个模型都很可能失败，而且预计很耗预算，BudgetFlow 会倾向于少投入或停止，把共享预算保护下来。

这套路由可以迭代：如果 frontier mode 显示 strong coverage 主导，就提高 coverage signal；如果 Model Fit 主导，就提高 model-fit signal。

5. 这篇论文最值得讲清楚的价值

BudgetFlow 把 agent 系统从“单个请求怎么选模型”推进到“一个任务 batch 怎么共享预算”。

这也是实际组织问题：strong model capacity 是稀缺资源。BudgetFlow 让不同职能任务通过同一套 task-level signals 竞争预算；任务来源可以被记录，但不直接决定 strong model access。

数据说明任务之间确实有差异：有些任务便宜模型更划算，有些任务强模型更划算，还有些任务两个模型都失败。

因此我们需要的不只是一个 router，而是一个能同时看任务价值、模型收益、Estimated Token Cost、Shared Budget的 budget governance framework。

SWE-bench 是严格 verifier 的实例；同一套接口也可以迁移到客服、文档、表格、科研任务等有验收信号的 agent workload。
