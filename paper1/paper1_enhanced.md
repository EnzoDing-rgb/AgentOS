# 成本效益优化（Quality under Budget）

核心思路是把论文的“主目标函数”从“让系统不崩”提升为：**在预算约束下最大化输出质量**（cost-effectiveness）。

**目标 venue**：与路线一 / 二兼容（SE 或 Systems / AI 交叉均可）。

---

## 1) 核心叙事转向

如果担心审稿人把你归类为“另一个 AgentRM：让系统不崩”，可以把 Paper 1 的主叙事改成：

> **在预算约束下最大化输出质量（并保证交互体验不崩）。**  
> 系统机制（Governor / Preemption / Zombie）是约束与实现手段；论文的主目标函数是 **cost-effectiveness**。

这会让 RQ1–RQ3 的三层能力像是逐步逼近同一个优化目标：
- **RQ1**：把“外部 429 / 崩溃”变成“内部可控排队”，使 cost-effectiveness 可被稳定测量
- **RQ2（核心贡献）**：质量-成本权衡下的模型路由——在预算约束下把钱花在刀刃上
- **RQ3**：把尾部延迟与僵尸损耗纳入“有效产出”的定义，避免预算被低价值 / 卡死请求吞掉

---

## 2) 评估指标升级（除 P99 / TTFT 之外）

`paper1_design.md` 里主线指标以 **完成数 / 失败率、成本、TTFT P99、平均质量** 为主。为了让论证更“像 SE 实证研究”（尤其是投 ICSE/FSE/TSE/TOSEM），建议在扩展实验 / 附录里补三类指标：**质量加权完成、预算效率、质量-成本 Pareto**。

### 2.1 Quality-weighted 完成率（不只是数量）

动机：很多策略会把“完成数”做高，但如果完成的大多是低质量输出，工程意义有限。需要一个把**完成**与**质量**合到同一个数里的指标。

- **QWCR（Quality-Weighted Completion Rate）**：令每个 turn 的终态质量 \(q_i \in [0,1]\)。若 turn 失败或被回收，则 \(q_i=0\)。定义
$$\text{QWCR}=\frac{1}{N}\sum_{i=1}^{N} q_i$$
全都高质量完成时接近 1；大量失败 / 低质量时下降。

- **QW-Completed（质量加权完成数）**：
$$\text{QW-Completed}=\sum_{i=1}^{N} q_i$$
把“完成数”从整数推广到“有效完成量”，适合对比不同 workload 大小或做横向汇总。

\(q_i\) 来源：
- **Mock 主线**：使用 `completed` 事件里（或该 turn 对应 backend 调用记录里）的 `quality_score`；失败 / 回收记为 0
- **RealBackend 补充实验**：按 `task_type` 用确定性 grader 得到 `quality_score`（见 `paper1_design.md §3.3`）

### 2.2 Budget efficiency（钱花得值不值）

动机：RQ2 / RQ3 里仅看“cost_total_usd 是否接近预算”还不够，需要衡量**每一美元换来的有效质量产出**。

- **Quality per Dollar（Q/$）**：
$$\text{Q/\$}=\frac{\sum_i q_i}{\text{cost\_total\_usd}}$$
单位成本换来的“有效完成量”，适合回答“钱花得值不值”。

- **Weighted Q/$（WQ/$，可选）**：若 workload 提供 `difficulty_weight`（见 `paper1_design.md §7.1`），令权重 \(w_i\)，则
$$\text{WQ/\$}=\frac{\sum_i w_i q_i}{\text{cost\_total\_usd}}$$
把“关键 / 难任务”的质量收益放大，更贴近“把钱花在刀刃上”的论点（RQ2 叙事）。

实现备注：
- 分母 `cost_total_usd` 直接来自 `summary.json` 或从 `events.jsonl` 汇总 `settlement_usd`
- **防坑**：若某 policy 因预算耗尽导致 cost 很低、几乎没做事，Q/$ 可能虚高。因此建议在同图里**同时报告 QWCR 与 Q/$**

### 2.3 质量-成本 Pareto 分析

把论文图表从“完成率 / 成本”升级为“质量-成本 Pareto”：
- 横轴：`cost_total_usd`
- 纵轴：`QW-Completed` 或 `QWCR`
- 画出不同 policy 的点云 / 均值 ± CI，并报告 Pareto frontier

这样审稿人更容易接受以下 claim：
- “我们的策略不是单纯更快 / 更稳，而是在同预算下把质量做得更高”
- “在同质量目标下，我们用更少的钱（或在同钱下，我们拿到更高质量）”

## 3) 形式化问题陈述：预算约束下最大化质量

把一次 run 写成一个优化问题。设 workload 有 \(N\) 个 turn，每个 turn \(i\) 可选择后端 \(a_i \in \mathcal{A}\)（例如 expensive / cheap）：

- 成本：\(c_i(a_i)\)（USD）
- 质量：\(q_i(a_i) \in [0,1]\)
- 总预算：\(B\)

最直接的形式化是 0-1 背包 / 多选择背包的变体：

$$\max_{a_1,\dots,a_N}\ \sum_{i=1}^{N} w_i\,q_i(a_i) \quad \text{s.t.}\quad \sum_{i=1}^{N} c_i(a_i)\le B$$

其中 \(w_i\) 是任务权重（可直接对应 `paper1_design.md §7.1` 的 `difficulty_weight`；没有就取 1）。

这个形式化写论文时很好用，可以把对照组的差异讲清楚：
- **Baseline A（总是高质量）**：很快触发预算约束 → 目标函数未必最大
- **Baseline B（逐请求贪心性价比）**：不考虑全局预算时序 → 可能把预算花在低权重 turn
- **Baseline C（全局预算感知但不看 task_type / 权重）**：相当于用粗糙的 \(w_i\)（全 1）近似
- **AgentOS**：显式利用 \(w_i\)（或 task_type / priority 信号）近似“价值”，把 budget 分配给高边际收益的 turn

## 4) ModelSelector 的设计原则：边际性价比排序

现在的实现是规则路由（质量及格线 + `budget_factor` 三档阈值）。给它一个更清晰的设计原则（强调直觉，不追求严格定理）：

**核心直觉**：在预算有限时，最合理的做法是把“更贵的选项”留给“边际收益 / 边际成本”最高的 turn。按下式排序：

$$\text{score}(i)=\frac{w_i\,\Delta q_i}{\Delta c_i}$$

其中 \(\Delta q_i = q_i(E) - q_i(C)\)、\(\Delta c_i = c_i(E) - c_i(C)\) 分别是 expensive 与 cheap 后端的质量差与成本差。

接回 AgentOS 实现：
- 把 `task_type / priority / difficulty_weight` 当作 \(w_i\) 的显式近似
- 把 `quality_prior` 差值当作 \(\Delta q_i\) 的估计
- 把 token 估算与价格表当作 \(\Delta c_i\) 的估计
- ModelSelector 可被解释为：在在线场景里用 `budget_factor` 做一个“预算乘子 / 阈值”来近似上述排序结果

承认现实中 \(q_i, c_i\) 不可完全知道，因此使用先验估计 + 在线预算信号；用实验展示鲁棒性（RQ2 的对照 C 正是为了排除"只是控预算更好"的解释）。

## 5) 连续质量的深层洞察：QCAS 设计视角

经典 OS 调度（例如 MLFQ）隐含了一个前提：任务的“收益 / 完成”近似二元（跑完 / 没跑完），优化多围绕吞吐、等待时间、公平性。

LLM agent 调用的关键不同点是：**质量是连续的**，并且通常可以通过增加成本（更强模型、更长输出、更大上下文）来提高质量，形成**质量-成本曲线**。

把每个 turn \(i\) 的“决策”从选一个后端，升级为选一个**质量水平** \(q_i \in [0,1]\)（或等价地选一个“推理预算 / 模型强度”），一次 run 的核心问题变成：

$$\max_{q_1,\dots,q_N} \sum_{i=1}^{N} w_i\,q_i \quad \text{s.t.}\quad \sum_{i=1}^{N} c_i(q_i) \le B,\ \ \text{SLO constraints}$$

这不是简单“调优先级”，而是把调度变成：**在预算约束下，把质量配额分配给不同 turn**。

**设计原则（作为直觉而非定理）**：

预算最优的结构通常不是“谁优先谁先跑”，而是“把每个 turn 推到同一个边际性价比水位线”。整个系统存在一个隐式的“预算影子价格”：
- `budget_factor` 可以被解释为对它的在线估计：花快了（影子价格高）→ 降低目标质量门槛；花慢了 → 提高目标质量门槛
- “质量及格线 + budget_factor 调门槛”是对这种水位线结构的工程化、可解释近似

**一句话升维洞察**：

> LLM 调用的输出质量不是 binary 的，它是连续谱；因此资源分配的核心不再是让更多 job 完成，而是决定**每个 job 应该被推到多高的质量水平**。

一旦接受这点，很多设计选择就从“经验规则”变成“优化结构的自然结果”：
- **为什么要区分任务价值 \(w_i\)**：线性目标里 \(w_i\) 直接决定了最优分配的质量水平
- **为什么要动态预算适应**：在线场景里预算影子价格必须随运行进度更新
- **为什么要把僵尸当作止损**：僵尸相当于把成本推到极端高、但质量不增长（边际收益 ≈ 0），任何合理策略都会把它截断

**可选拔高**：把 TTFT/P99 写成 penalty（例如 \(-\alpha \cdot \text{TTFT}\)）或 SLO 约束，就得到"质量-成本-体验"三目标问题，可以被解释为**多水位线结构**（预算影子价格 + 交互体验影子价格）。

### 5.1 直觉解释（把“连续质量”说清楚）

传统系统里很多任务的结果近似是 0/1 的：编译成功/失败、SQL 返回/超时、HTTP 200/500。调度器因此天然围绕“让更多任务跑完、别饿死、别超时”来优化。

但 LLM 不一样：它几乎总能“给你个答案”，差别在于答案好坏。比如同样是写一段代码：
- 用 **GPT-4 + 长 context + 思维链**：可能接近可直接合入（质量 0.95）
- 用 **GPT-4 + 短 prompt**：能跑但有小 bug（质量 0.7）
- 用 **GPT-3.5**：能跑但很糙（质量 0.5）
- 用更便宜的小模型：可输出但错误多（质量 0.3）

这四种都“完成”了，但质量在 \([0,1]\) 上连续变化；并且你通常可以通过增加成本把质量推高。于是调度问题从“让谁先跑、谁能跑完”，变成“预算有限时，每个任务应该被做到多好”。

一个具体化的例子：你有 $10 预算、100 个任务。
- **binary 思维**：追求 100% 完成率 → 全用最便宜模型，每个任务质量 0.3，表面都完成了但产出不可用
- **连续质量思维**：把关键的 20 个任务推到 0.95，其余 80 个推到 0.5 → 完成率仍然 100%，但**真正有用的产出**更大

因此可以把一句话作为全文直觉锚点：**资源分配的核心不再是让更多 job 完成，而是决定每个 job 应该被推到多高的质量水平。**

---

## 6) 系统机制的重新定位（作为优化约束）

当主叙事换成 cost-effectiveness 后，Governor / Preemption / Zombie 的位置更自然：
- **Governor**：保证预算约束与限流约束“硬成立”（否则优化问题本身不 well-defined）
- **Preemption**：把交互体验作为约束（TTFT P99 视作 SLO）或作为目标函数中的 penalty
- **ZombieDetector**：把“无效燃烧成本”从目标函数里剔除（否则 Q/$ 被噪声污染）

## 7) 写法建议：三段式结构

既显得硬核，又不把自己逼死（尽量不引入额外理论负担）：
- **问题定义段（主文）**：给出连续质量模型与优化问题形式化，强调设计原则（边际性价比水位线）为直觉，不强求完整定理
- **系统段（主文）**：说明 AgentOS 的启发式如何对应在线近似（budget_factor、quality threshold 对应预算影子价格的动态估计）
- **实证段（RQ2/RQ3）**：用 QWCR、Q/$、Pareto frontier 证明“我们确实更接近这种最优结构”，而不是只靠类比

一句话版结尾（可放 extended abstract 或摘要草稿里）：

> 我们将 LLM 调用治理表述为一个 **budget-constrained quality maximization** 问题；系统机制保证约束成立，而路由策略实现了边际性价比导向的在线近似，并在真实 workload 上达成更好的质量-成本 Pareto。
