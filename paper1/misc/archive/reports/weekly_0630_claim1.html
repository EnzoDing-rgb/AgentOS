BudgetFlow 周报

覆盖 2026-06-28 到 2026-06-30 的 Claim 1 主线工作。重点是把 Claim 1 从“单轮输赢”扩成一个更立体的 operating-condition matrix：什么时候 BudgetFlow 创造价值，什么时候 pure T3 是真实 frontier，什么时候 learned router 已经非常强。

Claim 1 立体化

当前最重要的正信号已经成立：BudgetFlow 不需要被表述成“永远打赢 T3”。更准确的论文说法是：在一个共享硬预算下，BudgetFlow 的目标是最大化 Total Resolved Value；我们现在既有 BudgetFlow 明确获胜 的条件，也有 pure T3 frontier-dominance 的条件，还有 learned-router 很强的压力测试条件。

这让 Claim 1 从单点结果变成了边界清晰的机制研究。论文价值不再只是“赢没赢”，而是“何时 value-aware allocation 有价值，何时 strongest model 自身就是最优 frontier”。

Related Work / OpenSquilla

这轮 related work 调研的核心结论：OpenSquilla / Claw-SWE-Bench 对我们不是“论文没价值了”的致命打击，而是把我们的边界逼得更清楚。

OpenSquilla 带来的压力

它已经把 per-turn/per-session 的 cost-per-success、tier routing、reasoning policy、replay、diagnostics、cache continuity 和工程工艺做得很强。Claw-SWE-Bench 也已经把 fixed protocol、cost reporting、Pareto frontier、Lite subset selection 这套评测方法做出来了。

我们仍然有的边界

BudgetFlow 的 Claim 1 不是“会 routing”也不是“会省钱”，而是：固定任务批次 + 共享硬预算 + 预注册任务价值 + verified outcome + 跨任务 allocation。公开资料里，OpenSquilla 还没有把这一整层 batch-global value-aware allocation 做出来。

问题 OpenSquilla / Claw-SWE-Bench BudgetFlow 当前定位
优化对象 session 内 cost-per-success；固定协议下的 harness / model cost-accuracy frontier 一批任务共享一个 hard budget 时的 Total Resolved Value
决策粒度 per-turn / per-session / per-harness cross-task batch allocation

Baseline 和 BudgetFlow 功能解释

对象 它是什么 它在测什么 为什么保留它
pure T2 所有任务统一走 T2 测“低单价”本身是否足以形成更优 frontier 它提供便宜 tier 的真实下边界，没有它就不知道 batch 里有没有 T2 room。
pure T3 所有任务统一走 strongest model 测 strongest model 是否已经是 shared-cap 下的最优 frontier 它是最强纯 tier 边界。BudgetFlow 输给它时，论文应报告 frontier，而不是削弱 baseline。
RouteLLM-inspired learned router 用离线 task features 和 frozen historical outcomes 学一个 task-level T2/T3 router 测“普通 learned routing 已经很强时”，BudgetFlow 是否还有 batch-global 增益 它逼着论文把贡献说清楚：增益来自 shared-budget governance，不是泛泛的“routing 更聪明”。
budget-only baseline 看到 budget pressure 和 generic per-task hard cap，但不读 Task Value 测结果是不是单靠预算压力就能解释，而不是 Task Value 真正增加了 allocation value 它把“budget-aware”和“value-aware”拆开，防止把所有效果都归因到 BF 身上。
BudgetFlow task-level 在固定任务顺序下，结合 compiled budget、Task Value、Model Fit 和 live remaining budget 做治理 直接测 Claim 1：同一 shared hard budget 下，能否拿到更高 Total Resolved Value 它必须和上面四类诊断镜子一起看，论文才能解释赢法、输法和边界。
BudgetFlow 功能 作用 在 Claim 1 里的位置
Budget Compiler 运行前根据任务集、ValueSource、Estimated Task Token Demand、tier catalog 和 calibration evidence 编译 shared cap 与 task runway Claim 1 的前半段。它决定我们研究的是哪一种 budget condition。
BudgetFlow Runtime 按固定任务顺序执行，跟踪 live remaining budget，决定 spend / continue / stop / stronger tier usage Claim 1 的执行层，负责把编译后的预算真正变成 allocation 行为。
Task Value 预注册价值信号，不在结果出来后追着改 把目标从 pass count 扩成 Total Resolved Value，但必须配 sensitivity 一起报告。
Frozen Router Plan / Model Fit prior 为 learned-router baseline 和 BF 冷启动提供静态先验 它是诊断工具，不应退化成 hardcoded answer key。
per-task hard cap / runway 避免单任务失控烧钱，同时仍然受 shared remaining budget 裁剪 保证系统既有止损，又不把 planned budget 误当平均切片。
stall guard / stop-continue discipline 在无进展、无 patch、无效循环时止损 服务 Claim 1，避免预算浪费在低价值空转，而不是单独追求省几分钱。
Value-Triggered Escalation 在高价值任务上有界地给 stronger tier 一个窗口 解释为什么 BF 既不是死板 all-T2，也不是无条件 all-T3。
Cost / Routing / Escalation Memory 记录 cost sufficiency、route outcome 和 stronger-tier productivity 更接近 Claim 2 机制层的增强，不是当前 Claim 1 成立的前提。
audit / replay / sensitivity 从同一 completed JSONL 重放 value profiles、KV recost、budget replay、frontier buckets 和 oracle gap 这是 reviewer defense 的主体，用来回答“为什么赢/为什么输/哪种条件会翻转”。

每轮怎么解读

4×30 的赢法

这轮最重要的不是“多过了几个任务”，而是 BudgetFlow 用更少总 spend 拿到了更高 TRV。典型例子是它保住了 pallets__flask-4992 这类高价值任务，抵消了 pure T3 多拿的 normal-value tail tasks。

5×30 clean 的负结果

这里不能硬把它写成“策略失败”。更准确的是：该条件下 pure T3 已经是非常强的 frontier。便宜模型不等于更省钱，如果 multi-turn 很长、T3 turn-efficient，很可能 strongest model 反而总成本更低。

resumed frontier-fix 的意义

这一轮把论文叙事真正补全了。现在我们不只有边界和负结果，也有一个完整 5-policy 主表的正结果，说明 BudgetFlow 不是只能“解释失败”，而是在合适条件下确实能赢。

一句话总结当前 Claim 1：BudgetFlow 的价值不是“永远比 T3 强”，而是识别并利用 shared-budget frontier 中真正存在的 allocation room；而当 allocation room 消失、pure T3 自身就是边界时，系统也应该诚实报告这一点。

现在论文怎么写

主结论：Claim 1 现在可以写成一个更完整的正结果加边界分析，而不是单点 victory lap。

  • 主表用 resumed frontier-fix 5×30：BudgetFlow 是 strongest current positive signal。
  • 4×30 作为最清晰的 value-aware allocation case：BF 虽然少过 1 个任务，但 TRV 与 TRV/$ 更高。
  • 5×30 clean 和 learned-prior final 作为 boundary case：说明 strongest model 有时就是正确 frontier，BudgetFlow 应报告 gap-to-frontier，而不是伪装成 all-T3。
  • Related Work 里明确承认 OpenSquilla / Claw-SWE-Bench 的工艺强度，但把我们的贡献收缩到 batch-global shared-budget value allocation 这一层。

给导师/审稿人的一句人话：我们不是造出了一个永远赢 strongest model 的神奇路由器；我们做的是一套 shared-budget governance framework，并首次把它在 SWE-bench mini 上做成了可验证、可审计、可报告边界条件的 Claim 1 证据体系。
