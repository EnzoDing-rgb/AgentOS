# BudgetFlow: 面向Agent工作流的动态预算路由机制

## 论文大纲

**怎么读**：问题与贡献 → 相关工作总表 → **BoPO** → 「按次问模型」与「操作系统式」两类对照 → vLLM 类比定位 → 附录（集成与栈图）。

---

## 1. 论文主线

- 一条或多条完整的智能体流程里，每一步都要调大模型，钱和接口额度都有限。我们关心的是：能不能用「流程走到哪了、哪一步更关键、还剩多少钱」这类信息，在**整条流程**上把钱花在刀刃上，而不是只看单次请求。
- 更具体一点：优化对象从「一次调用」变成「整条流程」，多条流程还共用同一个花钱上限、以及各后端的每分钟次数和并发上限。显式记录流程状态，会不会在**固定总预算**下提高成功率？如果会，好处主要来自控花钱节奏、步骤重要程度、对进展的判断，还是来自「多条流程之间谁先谁后」？我们希望把这件事说清楚、能复现、能做消融实验。

---

## 2. 本文的三个研究问题与独特贡献

### 2.1 三个研究问题

| 编号 | 问题 | 主要看什么 |
| :--- | :--- | :--- |
| **问题一** | 多条流程并行、总预算和后端限流都卡死的时候，钱浪费在哪、哪种限制最先卡脖子？ | 超预算比例、被限流（如 429）比例、排队多久、能收回多少预算、所谓「僵尸」任务被砍掉多少等 |
| **问题二** | 同样多的钱，如果每一步选大模型还是小模型时参考「流程阶段」，会不会比「只按整条流程粗分」或「只看预算不看阶段」修好更多 SWE-bench 类题目？ | 固定预算下有多少题被修好；对比「完整方案」「只在流程级路由」「只在步骤级按预算选」等 |
| **问题三** | 经常换模型会打乱前缀缓存；在这种前提下，按阶段调度还有没有净收益？ | 换模型有多频繁、首包延迟、缓存命中的 token 比例；对比「完整方案」和「尽量不换模型」等 |

### 2.2 独特贡献

1. **质量用连续刻度**：0 到 1 的进展度，而不是只做 0/1 成败。
2. **预算必须守住，但花钱节奏可以调**：用 `budget_factor` 一类信号反映「钱还够不够花、该不该省」。
3. **任务有多重要可以明说**：调用方给一个权重 \(w_i\)，解释得清。
4. **明显在烧钱的流程要敢停**：花了钱却不见进展，就截断，避免占着坑不产出。
5. **默认可免训上线**：规则和启发式路由；与需 RL 训练的方法（如 BoPO）对照见 §6。

## 3. 项目架构

```
多条智能体流程，每条有 N 次大模型调用，一共 J 条在跑
        │
        ▼
═══════════════════ BudgetFlow ═══════════════════
│ 【管钱和限流】Governor                         │  ← 路由策略可换，本层接口稳定
│   预算先预留再结算、按后端限流、控制并发能进多少 │
│                                              │
│ 【选模型】ModelSelector（可替换）               │  ← 唯一「谁用哪个模型」的策略
│   默认：估计这一步能带来多少进展 + 当前预算压力 │
│   也可换成：BoPO 等逐步 RL 路由、CARROT 等      │
│                                              │
│ 【止损与抢占】ZombieDetector + Preemption      │  ← 同样与具体路由算法解耦
│   砍掉僵尸调用；需要时可抢占交互式任务         │
│                                              │
│ 【多条流程怎么排队】Multi-Workflow Scheduler   │  ← 与具体路由算法解耦
│   跨流程协调、谁先进谁后进                      │
═══════════════════════════════════════════════
        │
        ▼
多个大模型后端 → 写事件日志 → 算实验指标
```

## 4. 相关工作分类

- 操作系统式资源管理：AgentRM, AgentCgroup, AIOS, pMVX
- 按「每一次提问」在强弱模型间路由：RouteLLM, CARROT, OmniRouter
- 单条智能体轨迹上逐步用强化学习选档：BoPO
- 用强化学习训「路由器」、短回合内工具式调用多模型（非整条 agent 工作流阶段）：xRouter
- GPU 上服务端的预算控制：Athena-Serve
- 硬件与云上整条工作流的编排：Murakkab

### 论文写到哪里、不写什么

**本文要写清楚的**

- **只有一个出钱方**：多条流程共用一笔总预算和后端的每分钟次数、并发上限；记账、谁能进、结算、僵尸检测、多流程调度，都是本文的运行时问题。
- **决策粒度**：流程里每一次大模型调用，加上全局还剩多少钱、各后端有多忙；实验里经常用 SWE-bench Verified 一类设置：很多实例一起跑、总预算卡死。

**本文不抢功、留给以后的工作**

- **多租户**：不同团队各自预算和服务等级协议——自然的下一步，和后面「对照 vLLM 讲故事」里第二阶段一致。
- **不取代 GPU 推理引擎论文**：不声称比 Athena-Serve、vLLM 在 KV 缓存、批处理上更全；本文管的是**智能体流程怎么花钱、每步配额**。
- **僵尸检测**：是运行时里的一块，可以做消融；不是单独贡献一整套机器学习理论。
- **成本怎么计价**：不绑具体厂商价目；用抽象的美元或 token 就能复现实验结论。

## 6. 和本文最接近的论文：BoPO

**Budget-Aware Agentic Routing via Boundary-Guided Training**（Zhang et al., arXiv:2602.21227，2026）。**BoPO** 是 **Boundary-Guided Policy Optimization** 的缩写：在智能体的**每一步**用强化学习在强弱模型间选档；以边界引导类训练缓解稀疏回报（具体算法细节以原论文为准）。原论文分析与实验环境主要为 **ALFWorld、SciWorld、AppWorld** 一类长程 agent 设定，**不是**以「多路 SWE-agent 共享一笔总预算」为叙事主轴。

### 6.0 勿把本文独创叙事写进 BoPO

**BoPO 原文不包含**所谓 *un-stabbed / stabbed chatroom* 或多 agent「会话房」式编排。若你在讲 **stab 拆成多个 agent** 等，那是**本文或工程上的扩展/独创路线**，幻灯片与论文对比里**不要归因为 BoPO 的贡献或设定**。

### 6.1 和本文是什么关系（先讲层级，再对表）

BoPO 训练出来的是**单条任务、逐步选模型**的策略，在我们系统里正好可以放进 **ModelSelector** 当一种实现。本文多出来的是**运行时底座**：全局记账（先占坑再结算）、硬预算、后端每分钟次数和并发、多条流程谁先做、僵尸任务砍掉等。没有这层底座，BoPO 单独**解决不了**「很多流程同时跑、共用**同一个**总预算和接口配额」这种系统级问题；反过来，**可以把 BoPO 接进 ModelSelector**，由底座保证不超标，再让 RL 策略在允许范围内发挥。

### 6.2 例子：分清 BoPO 论文设定 vs 本文主测

- **BoPO（对齐原论文与 concept §9）**：单条长程任务、**任务内**模型预算与逐步选档；环境与指标围绕 **ALFWorld / SciWorld / AppWorld** 等，不在大纲里误写成「BoPO 在 SWE-bench Verified 上批跑共预算」。
- **BudgetFlow（本文）**：仍可用「读 issue → 搜仓库 → …」帮助听众理解**逐步花钱**；但**我们论文常测的**是多实例**同时**跑、共用 \(B_{\text{total}}\)、全局「下一笔谁调用」、 harness 总体修好多少题——这是**底座 + 多 workflow**，不是 BoPO 一文单独解决的问题。

### 6.3 本文和 BoPO 对照（一张表说完）

| 方面 | BoPO | BudgetFlow（本文） |
| :--- | :--- | :--- |
| **做法** | 强化学习，要数据和算力训练 | 启发式，免训练；**BoPO 训好的策略可以插进 ModelSelector** |
| **好不好讲清楚** | 策略像黑盒 | 用「加权进展 / 额外美元」与 **`budget_pressure`** 等显式量，能说清为什么这样选 |
| **预算是什么意思** | 训练时软约束、推理时再配合别的方法 | 运行时必须守住硬顶，先预留再结算；和 BoPO 那套账本不是一回事 |
| **任务有多重要** | 隐含在奖励里让模型学 | 调用方显式给权重 \(w_i\) |
| **典型优化目标** | **一条任务**里花钱和成功率怎么权衡 | **很多人共用一个上限**时，总体完成率（或类似系统指标） |
| **决策时看多远** | 只看**当前这条轨迹**和这条任务剩多少钱 | 看全局账本、**跨多条流程**谁排在队首 |
| **止损和回收** | 没有专门讲这一块 | 僵尸检测、抢占、释放预留和占住的并发位 |
| **限流和 429** | 不是论文主战场 | 生产里要管的：准入、配额、被限流怎么办 |
| **换场景要不要重训** | 换域往往要重新训 | 冷启动就能用，接不同框架也相对容易 |
| **能不能一起用** | 只管逐步选模型，**替代不了**全局底座 | 我们的启发式可当 RL 的**冷启动对照**；底座也能托住 BoPO 的决策 |

### 6.4 BoPO 没写、本文要补上的差分

- 多条智能体**共用一个总预算**时，谁多谁少、「前面花光、后面饿死」
- 生产里 **RPM、并发**、被限流后的治理
- **僵尸或没进展**的任务占着预算和位置怎么收回
- **本地推理、KV 缓存**切换带来的代价怎么显式考虑
- **没有大量本域数据**时，不靠训练也能先跑起来

## 7. 和其他工作的差别（BoPO 已单讲，这里只讲另外两类）

**BoPO** 已在专节讲过；**xRouter** 未单开一节。这一节只对比两类：**每次提问单独选模型**的工作，和**像操作系统一样管机器资源**的工作。总表里的几列含义，就是上一节表头那三句「共用一个上限吗、按步骤选吗、要不要大训一把」。

### 7.1 对比「按次问模型」的几篇（RouteLLM, CARROT, OmniRouter）

| 方面 | 按次问模型的路由 | **本文** |
| :--- | :--- | :--- |
| **决策** | 每条查询各自优化 | **整条流程多步**一起受总预算约束 |
| **记不记状态** | 基本不记流程级状态 | 记还剩多少钱、花钱快慢等 |
| **预算** | 不管或只估单次查询花多少 | **总预算硬约束** |
| **任务重不重要** | 不区分 | 用 \(w_i\) 显式区分 |

### 7.2 对比「操作系统式」几篇（AgentRM, AgentCgroup, AIOS, pMVX）

| 方面 | 操作系统式工作 | **本文** |
| :--- | :--- | :--- |
| **主要矛盾** | 稳定、隔离、别互相拖死 | **花钱和效果**怎么权衡 |
| **优化什么** | 延迟、吞吐、隔离 | 质量、成本、以及两者之间的权衡 |
| **管的资源** | CPU、内存、并发、RPM 等 | **大模型调用**的质量和成本 |

## 8. 叙事：为什么拿 vLLM 类比

- vLLM 是伯克利 2023 年开源的推理引擎（SOSP 2023）。第一篇论文想的是：**只有一家在用这台机器**时，怎么把很多请求 batch、调度好，吞吐做大。那时不管「很多家客户抢同一台机器」怎么分蛋糕。后来才有 Andes（OSDI 2024）、SGLang router 等，往**多客户、配额、服务等级**上走。
- 这是很常见的一条路：先把「单一责任方」下的核心机制做扎实，再在之上加**政策层**处理多方竞争。
- BudgetFlow 也按这条路：**这篇论文**先写「**只有一个出钱方**」——一笔固定预算，上面跑很多条智能体流程；我们做的是跨流程分钱的调度器，成本模型可以换（不强绑某一种计价）。
- 自然的下一步是**多租户**：不同团队各自预算和 SLA，共用同一套执行底层，会多出隔离、异构任务混跑时的配额仲裁等问题——**这篇先不展开**，但框架上能接过去。
- 多租户扩展时，调度器仍然可以**不关心每家具体用哪种模型、怎么计价**，仲裁层尽量保持通用。
- 所以定位可以一句话说：**以后多租户智能体算力分配的工作，可以建在这篇「单出钱方」的基础上。**
