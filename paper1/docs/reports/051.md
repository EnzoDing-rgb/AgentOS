## Task E — Claim-by-Claim Evidence

### First Claim (value-driven allocation): NO independent evidence

- BO and SB have **identical resolved sets** (13480, 13647, 14774, 16988). BF has a **worse** resolved set (13480, 13647, 14774 only — missing 16988).
- All strategies failed sympy-20212 (budget exhausted — scheduled last).
- No strategy demonstrated differential value allocation. The value spread existed in the task pool (4.87x), but all strategies either solved the same easy tasks or failed the same budget-starved task.
- **Verdict:** First Claim = "observability validated; independent evidence pending." Need experiment where strategies face different task pools OR budget allocation produces different selection.

### Second Claim (cost/routing efficiency): NOT supported — BF loses

| Metric | BO | SB | BF | Winner |
|---|---|---|---|---|
| Pass rate | 4/5 (80%) | 4/5 (80%) | 3/5 (60%) | BO/SB |
| Cost on 3 common solves | $0.1735 | $0.2111 | $0.2084 | BO |
| Avg turns (all) | 17.0 | 13.8 | 12.8 | BF |
| T3 usage | 13% | 14% | 36% | — |

BF is 20% more expensive than BO on the 3 tasks all strategies solved ($0.2084 vs $0.1735).
BF failed the hardest task (sympy-16988) despite spending $0.2519 and using 54% T3.

### KV/Cache Downside

BF on sympy-13480: 17 turns (vs BO's 5 turns) with `rescue_timeout_gold_edited` exit.
The rescue mechanism burned 12 extra turns on an already-solved task — consuming budget
that could have been allocated to sympy-16988 or sympy-20212. This is a confirmed
KV/cache downside: BF's adaptive routing over-invests in easy tasks, starving hard tasks.

### Stage-Weight Ablation (H3)

SB (equal weights, w_i=1/1/1) matches BO's pass rate (4/5) and has better cost profile
than BF on easy tasks. The stage-weight difference (w_i=1/3/2.5 in BF vs 1/1/1 in SB)
does NOT improve hard-task performance — BF failed sympy-16988 while SB solved it.

SB has the best RVPD on easy tasks (sympy-14774: $2.18, sympy-13480: $1.41) — suggesting
that on easy tasks, simpler routing works better.

## Known Blockers

1. **Batch cap too tight.** $0.50 for 5 tasks means the last task always starves (sympy-20212 failed for all 3 strategies due to budget exhaustion). Need either per-task caps or a larger batch cap.

2. **BF over-invests in easy tasks.** `rescue_timeout_gold_edited` on sympy-13480 (17 turns, 5 for BO) shows BF burns budget on already-solved tasks. The rescue mechanism needs a cost ceiling or earlier stop-loss.

3. **BF's T3 routing doesn't guarantee hard-task success.** sympy-16988: BF used 54% T3 but still failed (repair_fail). BO used only 5% T3 and passed. T3 ≠ success guarantee.

4. **Identical resolved sets prevent First Claim testing.** With all strategies solving the same easy tasks and failing the same hard task, there's no value-allocation signal. Need either: (a) a larger task pool with heterogeneous difficulty, (b) different budget allocation per strategy, or (c) a budget-pressure experiment where strategies must pick which tasks to fund.

5. **Task ordering effect.** sympy-20212 (mid-difficulty) failed for all strategies because it was scheduled last and budget was exhausted. Task order within a shared-budget batch confounds strategy comparison.

---

## Next Recommended Experiment

1. **Fix batch cap sizing.** Use `--tight 0.15` per task instead of $0.50 shared for 5 tasks. This ensures each task gets fair budget independent of batch position.

2. **Test 3-policy on harder task mix.** Add sympy-17630 and sympy-18057 (from value matrix, difficulty 0.23-0.41) to see if BF's T3 escalation helps on genuinely hard tasks where T2 fails.

3. **Consider per-task budget instead of shared batch.** The shared batch governor penalizes later tasks. For First Claim testing, per-task caps isolate strategy performance from batch-ordering effects.

4. **Add rescue cost cap.** BF's `rescue_timeout_gold_edited` consumed 12 turns on an already-solved task. A rescue cap of 3-5 turns would prevent budget drain on easy tasks.
