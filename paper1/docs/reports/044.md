## Part B — Value-Aware Offline Re-Score Tool

### B.1 Implementation

- **Module:** `src/budgetflow/value_rescore.py` (~220 lines)
- **Tests:** `tests/test_value_rescore.py` (32 tests)
- **CLI:** `python3 -m budgetflow.value_rescore --input <jsonl> --profile <name>`

### B.2 Value Profiles

| Profile | `value_i` | Purpose |
|---------|-----------|---------|
| `equal` | 1.0 for all tasks | Backward-compatible baseline; reproduces old `cost_per_resolved` era |
| `heuristic` | Difficulty coefficient (see below) | Cold-start example; NOT a North Star commitment |
| `custom` | User-provided JSON mapping | Pluggable interface for future value models |

**Heuristic profile definition (clearly labeled, not North Star):**
- Base: historical difficulty coefficient from progress.md (anchor: sympy-20212 = 1.00×)
- Django modifier: ×1.1 (web framework bugs affect more users)
- Unknown tasks: 1.0 (neutral, no information)
- Known coefficients: 14774=0.15, 13480=0.31, 13647=0.82, 20212=1.00, 16988=6.58, 18057=2.50, 18189=2.00, 18621=1.50, 17630=1.80, django-10924=1.20

This is intentionally simple and auditable. A real value model should use task
features, historical outcomes, and organizational priority — not just difficulty.

### B.3 Metrics Produced

| Metric | Formula |
|--------|---------|
| `resolved_count` | count of `harness_resolved=True` |
| `total_cost` | sum of `total_cost` |
| `cost_per_resolved` | `total_cost / resolved_count` |
| `resolved_value` | `sum(value_i * resolved_i)` |
| `resolved_value_per_dollar` | `resolved_value / total_cost` |
| `value_weighted_budget_fail` | `sum(value_i` for unresolved tasks with budget-fail exit) |
| `resolved_rate` | `resolved_count / total_count` |

### C.3 Honest Assessment

**BudgetFlow does not beat BudgetOnly on any metric in available data.**

| Metric | 030 winner | 031 winner |
|--------|------------|------------|
| Resolved count | Tie (7) | Tie (4) |
| Total cost | BO ($1.59 vs $2.03) | BO ($0.49 vs $0.70) |
| Cost per resolved | BO ($0.23 vs $0.29) | BO ($0.12 vs $0.18) |
| Resolved value | Tie | Tie |
| Resolved value per dollar | BO | BO |

The routing overhead of BudgetFlow (more turns, more tier-switching) adds cost
without adding resolved tasks. This is consistent with the original 030/031
conclusions — the routing mechanism exists and operates, but on these easy-to-moderate
task pools the extra cost is not repaid in additional resolutions.

This does NOT mean BudgetFlow's first claim (value-aware governance) is false.
The current experiments use `value_i=1` implicitly — all tasks are equally
valuable, so there is no value-allocation decision to make. The first claim
requires tasks with unequal value to demonstrate that BudgetFlow can allocate
scarce budget toward higher-value tasks. The current data cannot test this.

## Part D — Routing Trace / Second-Claim Audit

### D.1 Data Available

Both 030 and 031 have per-turn traces with routing decision fields:
`stage`, `backend_tier`, `router_reason`, `router_scores`, `router_pressure`,
`router_branch`, `has_progress`, `progress_reason`.

### D.2 Findings

**Stage-aware routing exists and is directional:**
- BudgetFlow uses more T2 than BudgetOnly (030: BF 83% T2 vs BO 24% T2)
- REPAIR stage gets more T3 upgrades than LOCALIZATION (consistent with `repair_heavy` weight profile)
- `router_reason` shows two branches: `bf_full_max_tier=2` (stay cheap) and `bf_full_escalated_t3` (upgrade)

**Progress table is uncalibrated:**
- `router_scores` for tier2 is always 0.0 — no stage-tier progress differentiation
- `has_progress` is True on only 28% (030) and 21% (031) of turns
- No `expected_progress_gain` tracking per (stage, tier) pair
- The formula `stage_weight × expected_progress_gain / marginal_cost` exists in
  code but operates with a zero_calibration progress table

**Tier mix comparison (030):**

| Stage | BO T2 | BO T3 | BF T2 | BF T3 |
|-------|-------|-------|-------|-------|
| LOCALIZATION | — | — | 77 | 8 |
| REPAIR | — | — | 113 | 31 |
| VALIDATION | — | — | 5 | 1 |

BO was almost all T3 in 030 (76%) and mostly T2 in 031 (84%). This BO tier
inconsistency is a data-quality concern but does not affect the BudgetFlow
routing audit directly.

### D.3 Second-Claim Evidence Level: WEAK

| Criterion | Status | Detail |
|-----------|--------|--------|
| Stage-aware routing active | Yes | BF uses different tier mix than BO; REPAIR gets more T3 |
| Progress table calibrated | No | `tier2` score always 0.0; `has_progress` < 30% |
| `expected_progress_gain` used | No | Formula in code but table is zero_calibration |
| BF beats BO on cost or resolved | No | Tie on resolved, BO cheaper in all cases |
| KV/cache overhead measured | No | Not measured in any run |
| Evidence grade | **Weak** | Mechanism exists; operational benefit not demonstrated |

The second claim (stage/progress-aware routing improves per-step cost efficiency)
cannot be supported by current data. The routing mechanism is active and
directionally follows the weight profile, but without a calibrated progress
table or cost-efficiency evidence, it remains a hypothesis.

### D.4 What Would Strengthen the Second Claim

1. Calibrate `Progress[stage, tier]` from replay data (see paper1_concept.md §3.4)
2. Run a controlled comparison on a task pool with heterogeneous difficulty where
   BudgetFlow's routing can differentiate (easy tasks stay T2, hard tasks get T3)
3. Measure KV/cache overhead of tier switching
4. Compare BudgetFlow Full against BudgetFlow with `w_i=1` (stage_blind ablation)

## Part E — Paid Experiment Readiness

### E.1 Recommendation: Do NOT Start Paid Run Yet

**Reasoning:**

1. **No value differentiation in current data.** All re-scores show BO ≤ BF on
   cost and BO ≥ BF on val/$. The first claim requires tasks with unequal value
   to demonstrate value-aware allocation. Current task pools are too homogeneous.

2. **Progress table is uncalibrated.** The second claim's mechanism
   (`stage_weight × expected_progress_gain / marginal_cost`) cannot be tested
   without a calibrated progress table. A paid run with zero_calibration would
   produce the same "BO ≥ BF" pattern.

3. **No value model exists.** The first claim requires a task value assignment
   (which tasks are worth more?). Without this, even a heterogeneous task pool
   cannot test value-aware allocation.

### E.2 What Is Needed Before a Paid Run

| Prerequisite | Status | Priority |
|-------------|--------|----------|
| Value proxy design | Not started | P0 — blocks first claim |
| Progress table calibration | Not started | P1 — blocks second claim |
| Heterogeneous task pool | Available (10 tasks in 030) | P1 — need value assignment |
| BudgetFlow Cache-Sticky impl | Not started | P2 — KV/cache measurement |
| Stage_blind ablation (`w_i=1`) | Code exists but not run | P2 — ablation |

### E.3 Minimal Viable Paid Run Design (for future reference)

If the prerequisites are met, a small paid experiment should:
- Use 10 tasks with assigned value (not all equal)
- Compare: BO tight, BF tight, BF stage_blind (w_i=1)
- Budget: ≤ $5 total
- Readout: resolved_value @ fixed_budget, val/$, turn-level tier mix
- Progress table: at minimum, a replay-calibrated table from public SWE-bench trajectories

## Next Steps

1. **Design task value proxy.** This is the P0 blocker for the first claim.
   Options: difficulty-based, repo-based, user-provided priority tiers, or
   learned from historical outcomes.
2. **Calibrate progress table.** Replay public SWE-bench trajectories to fill
   `Progress[stage, tier]` before any paid run.
3. **Both claims must be tested separately.** First claim = value-aware allocation
   (needs value model). Second claim = stage/progress-aware cost efficiency
   (needs calibrated progress table + KV measurement).
4. **Do not scale until a small controlled run shows BF > BO on at least one
   metric.** Current data uniformly shows BO ≥ BF.
