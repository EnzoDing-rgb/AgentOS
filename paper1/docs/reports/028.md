# 028 — BudgetMemory Key Normalization Fix

## 1. What 027 Exposed

027 ran with `--budget-memory-exclude-ids` and reported 100% `strategy_median` source for ALL tasks — including sympy tasks that should have hit `repo_median`.

**Root cause: two independent normalization bugs.**

### Bug 1: Repo key mismatch

`_learn()` builds `_repo_stats` keys using `_extract_repo(instance_id)` = `"sympy"`.  
Runner passes `task.repo` = `"sympy__sympy"` (SWE-bench Mini repo slug) to `estimate_task_budget()`.  
`_repo_stats.get("sympy__sympy")` returns `None` → repo_median miss.

### Bug 2: Strategy hardcoded for all tasks

Runner passed `strategy="budget_only_tight"` for ALL estimates regardless of actual strategy. This meant:
- BudgetFlow tasks used BudgetOnly historical costs as their cap basis
- `strategy_median` was always `budget_only_tight`, mixing bo/bf cost distributions
- Cascade went exact_task → repo_median (miss due to Bug 1) → strategy_median (hit, but wrong strategy for bf)

## 2. Fix: normalize_repo_key()

```python
def normalize_repo_key(raw: str) -> str:
    """Normalize repo identifiers to canonical short key.
    
    Handles:
      instance_id:  "sympy__sympy-13480" -> "sympy"
      repo slug:    "sympy__sympy"       -> "sympy"
      repo slug:    "sympy/sympy"        -> "sympy"
      plain key:    "sympy"              -> "sympy"
    """
    if not raw:
        return raw
    return raw.replace("/", "__").split("__")[0]
```

Applied in:
1. `_extract_repo()` — used in `_learn()` to build `_repo_stats` keys
2. `estimate_task_budget()` — normalizes `repo` parameter before `_repo_stats` lookup

## 3. Fix: Remove hardcoded strategy

Runner and offline_replay no longer pass `strategy="budget_only_tight"` to `estimate_task_budget()`. The cascade is now `exact_task → repo_median → global_fallback`.

**Rationale**: Per-task cap is shared across strategies. Using one strategy's cost distribution (bo) to estimate another's (bf) is logically unsound. The clean approach is to not use strategy_median in the default cascade — let repo-level statistics handle multi-task repos, and global_fallback handle single-task repos.

`strategy_median` remains available as an explicit opt-in when caller passes `strategy=...`.

### Before vs After — estimate call

| path | before | after |
|------|--------|-------|
| runner (real) | `estimate_task_budget(iid, repo=task.repo, strategy="budget_only_tight")` | `estimate_task_budget(iid)` |
| runner (dry-run) | `estimate_task_budget(iid, repo=task.repo, strategy="budget_only_tight")` | `estimate_task_budget(iid)` |
| offline_replay (LOO) | `estimate_task_budget(iid, strategy=est_strategy)` | `estimate_task_budget(iid)` |
| offline_replay (dry-run) | `estimate_task_budget(iid, strategy="budget_only_tight")` | `estimate_task_budget(iid)` |

## 4. Source distribution: before vs after

There are two scenarios with different training sets. The cascade behavior is the same in both, but absolute numbers differ because global_fallback uses the training set's global median.

### Scenario 1: Full LOO (10 tasks, exclude 1 at a time)

Training set when django is held out: 138 records from 9 sympy tasks (including easy tasks like 13480, 14774). Global median = $0.11.

| source | before (strategy passed) | after (strategy removed) |
|--------|--------------------------|--------------------------|
| exact_task | 0/10 (0%) | 0/10 (0%) |
| repo_median | 9/10 (90%) | 9/10 (90%) |
| strategy_median | 1/10 (10%) | 0/10 (0%) |
| global_fallback | 0/10 (0%) | 1/10 (10%) |

The single shift: django moves from `strategy_median` ($0.11, from `est_strategy` in held-out records) to `global_fallback` ($0.21, from 138-record global median × 2.0). No strategy is passed → cascade skips strategy_median tier.

### Scenario 2: 027 task set (5 held out, 5 in training)

Training set: 70 records from 5 harder sympy tasks (17630, 18057, 18189, 18621, 20212). Global median = $0.15. This is the training set 027 actually used.

| task | 027 actual (broken) | after fix (dry-run) | source change |
|------|-------------------|---------------------|---------------|
| django__django-10924 | strategy_median $0.1514 | global_fallback $0.2968 | strategy_median → global_fallback |
| sympy__sympy-13480 | strategy_median $0.1514 | **repo_median $0.2120** | strategy_median → repo_median |
| sympy__sympy-13647 | strategy_median $0.1514 | **repo_median $0.2120** | strategy_median → repo_median |
| sympy__sympy-14774 | strategy_median $0.1514 | **repo_median $0.2120** | strategy_median → repo_median |
| sympy__sympy-16988 | strategy_median $0.1514 | **repo_median $0.2120** | strategy_median → repo_median |

027's 100% `strategy_median` was caused by Bug 1+2 together:
- Bug 1 (repo key mismatch): `task.repo="sympy__sympy"` didn't match `_repo_stats["sympy"]` → repo_median miss
- Bug 2 (hardcoded strategy): `strategy="budget_only_tight"` forced strategy_median hit for ALL tasks

### Why django differs across scenarios ($0.21 vs $0.30)

Both use `global_fallback` with the same 2.0x risk multiplier. The difference is purely in the training set's global median:

| scenario | training recs | global median | django est |
|----------|--------------|---------------|------------|
| Full LOO (9 sympy in training) | 138 | $0.1052 | $0.2104 |
| 027-exclude (5 harder sympy) | 70 | $0.1484 | $0.2968 |

Scenario 2's training set excludes the cheapest sympy tasks (13480 at $0.05, 14774 at $0.03), so the global median is higher. Both estimates are correct for their respective training sets. This is expected behavior for `global_fallback` — its accuracy depends on how representative the training set is.

## 5. What 027 Actually Proved

027's contribution is real but narrower than initially thought:

| claim | status |
|-------|--------|
| `--budget-memory-exclude-ids` prevents exact_task leakage | **Proven** (0/10 exact_task) |
| LOO experiment infrastructure works end-to-end | **Proven** (Gate B clean, no hangs) |
| BudgetMemory provides repo_median estimates for held-out tasks | **NOT proven by 027** (Bug 1 prevented repo_median hits) |
| bo_tight vs bf_tight at LOO scale | **Not reliable** — caps were wrong ($0.15 strategy_median for all) |

027 is valid as **plumbing/infra evidence** but NOT as **generalization evidence**. The repo_median tier was never exercised in the real run.

## 6. Should We Rerun 027?

**Decision: not yet.**

Reasons:
1. The normalization fix changes the cascade behavior meaningfully — sympy tasks would get $0.2120 caps (repo_median) instead of $0.1514 (strategy_median). This 40% higher cap could change budget_exhausted vs pass outcomes.
2. 027's pass results (4/5 both strategies) might have been influenced by the wrong caps.
3. Before rerunning, the offline LOO with correct normalization should pass Gate A cleanly (which it does — see section 4).

**When to rerun**: After settling on the cascade design (repo_median only vs repo_median+strategy_median with per-strategy estimates). The current design (no strategy_median in default cascade) is the simplest correct approach. If this is accepted, rerun 027 with correct normalization.

**Alternative**: Run 028 as a fresh 5×2 with fixed normalization, new run_series, and explicitly compare to 027's source distribution.
