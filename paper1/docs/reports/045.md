### B.3 Value Profiles

All profiles are pre-registered or cross-strategy. No BF-specific signals.

| Profile | Formula | Range |
|---------|---------|-------|
| `equal` | `1.0` for all tasks | [1.0, 1.0] |
| `difficulty` | `avg_cost × (1 + 0.5×(1 - resolve_rate))`, floor 0.01 | [0.01, 0.41] |
| `solve_rarity` | `1.0 + 4.0×(1 - rarity)^2` | [1.0, 5.0] |
| `combined` | `log1p(difficulty) + solve_rarity` | [1.0, 5.14] |

**Failure penalty rationale:** Tasks with lower cross-strategy resolve rates
get a penalty multiplier on the cost component. The penalty is capped at 1.5×
for 0%-solved tasks. This avoids over-weighting potentially impossible tasks
while still recognizing that hard-to-solve tasks are more informative.

**Solve-rarity rationale:** Tasks that fewer strategies can solve are more
discriminating — they separate good routers from bad ones. Everyone-solves
(rarity=1.0) and no-one-solves (rarity=0.0) are less informative than tasks
solved by exactly one strategy. The quadratic form gives moderate rarity
(0.2-0.5) meaningful weight without over-weighting impossible tasks.

### B.6 Robustness Sensitivity

Each task gets 5 sensitivity variants:

| Variant | Formula |
|---------|---------|
| `cost_only` | avg_cost (ignore solve rate) |
| `rate_only` | 2.0 - resolve_rate (inverted, ignore cost) |
| `cost_heavy` | avg_cost × (2 - resolve_rate) |
| `rate_heavy` | (1 + avg_cost) × (2 - resolve_rate) |
| `difficulty_default` | Current formula (cost + failure penalty) |

These variants allow sensitivity analysis: if conclusions hold across all 5
variants, they don't depend on a single magic number. The sensitivity dict is
embedded per-task in the value matrix JSON.

### B.7 Cross-Strategy Guarantee

All profiles are computed from `TaskRecord` fields: `avg_cost`, `resolve_rate`,
`solve_rarity` — all of which aggregate across ALL strategies seen in the JSONL
universe. No profile depends on which strategy achieved `harness_resolved=True`.
The `TestNoBFLeakage` test class (4 tests) verifies this invariantly.

### C.4 Key Finding: Selection-Bias Caveat Confirmed

**Negative deltas do NOT mean T3 is worse than T2.** T3 turns happen when the
agent is already stuck or under budget pressure — the harder cases get escalated
to T3. A raw comparison of progress rates would misleadingly suggest "T3 is
worse." This is a classic selection-bias pattern: treatment assignment (T3) is
correlated with difficulty.

The progress calibration output includes a per-delta caveat:
> "Negative delta does NOT mean T3 is worse — T3 turns are selected on harder
> situations."

### C.5 LOCALIZATION Progress Signal is Dead

LOCALIZATION has 0% progress rate across 215 turns (170 T2 + 45 T3). This means
the localization progress signal — checking whether the touched file is in the
gold patch — is not being populated in turn traces. This is a data-quality issue
that should be fixed before any paid run: without localization progress, the
router has no signal to decide whether to escalate during localization.

## Part D — Paid-Run Readiness (Updated)

### D.1 What Changed Since Phase N (044)

Phase N identified two blockers: (1) no paper-defensible value proxy, (2)
progress table uncalibrated. Phase O partially addresses both:

| Blocker | Phase N Status | Phase O Status |
|---------|---------------|----------------|
| Value proxy design | Not started | **Framework built** — 4 profiles, sensitivity, pluggable custom |
| Progress table calibration | Not started | **Calibrated** — from existing traces, with selection-bias caveat |

But "framework built" is not the same as "ready for paper claims":

- **Value proxy:** The framework exists and is tested, but the *specific value
  model* for a paper claim is not yet chosen. The `combined` profile (log1p +
  solve_rarity) is a reasonable heuristic but needs justification. The `custom`
  profile interface allows injection of any value model later.

- **Progress table:** Calibrated from 639 turns, but (a) LOCALIZATION signal is
  dead (0% rate), (b) the selection-bias means we cannot naively use these rates
  as expected_progress_gain in the routing formula.

### D.2 Recommendation: Still Do NOT Start Paid Run

The core issue from Phase N remains:

1. **No value differentiation in current task pool.** All 10 tasks have both BO
   and BF trying them. The resolved task sets are identical between strategies.
   Value profiles only matter when strategies resolve DIFFERENT tasks.

2. **Progress table can't be naively plugged into routing.** The calibrated
   rates are confounded by selection bias. Using them directly as
   `expected_progress_gain` would encode the bias into the router.
