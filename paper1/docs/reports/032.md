# 032 — Runner Path Audit (Phase B Read-Only)

**Date:** 2026-06-04
**Branch:** `feature/issue-1` @ `b42b35a`
**Status:** Audit only — no code changes

## Purpose

Map every artifact the runner creates to its filesystem location, classify each
by persistency, resumability, NFS risk, and Git pollution risk.  Identify the
locations that must move before jobs>1 can be safely restored.

### 031 (5x2, auto-budget + BudgetMemory with LOO exclusion)

| Field | Value | Note |
|---|---|---|
| `auto_budget_enabled` | True (all 10 rows) | Auto-budget was used |
| `budget_prior_source` | `history_exact` (all 10 rows) | From `_HISTORICAL_PRIOR` hardcoded table |
| `budget_memory_enabled` | True (all 10 rows) | BudgetMemory was loaded |
| `budget_memory_budget_source` | `repo_median` (all 10 rows) | 5 held-out excluded, sympy has 8 records in training |

**Interpretation:** Two independent source systems agree with their design:
- Auto-budget (`budget_prior_source`): hardcoded prior has individual cost data
  for all 10 SWE-bench tasks → `history_exact`. This is cold-start data, not
  experiment leakage.
- BudgetMemory (`budget_memory_budget_source`): learns from JSONL with LOO
  exclusion → held-out tasks cascade to `repo_median`. Zero `exact_task`
  leakage.

### Source Field Semantics

| Field | Set By | Meaning | Leakage Risk |
|---|---|---|---|
| `budget_prior_source` | `AutoBudgetEstimator` (auto_budget.py) | Which prior was used for cap estimation | Low — hardcoded cold-start table |
| `budget_memory_budget_source` | `BudgetMemory` (budget_memory.py) | Which cascade level was hit for statistical estimate | **High** — this is the LOO validation metric |

**These two fields MUST NOT be conflated.** Confusing them would misinterpret
`history_exact` as BudgetMemory leakage when it's actually auto-budget's
independent cold-start prior.

## Current Concurrency Safety

The `_repo_git_lock()` context manager (`local_harness.py:114`) uses fcntl.flock
on per-repo lock files under `/tmp/budgetflow_locks/`. The lock is held only
during `git worktree add` and `git worktree remove` operations.

**What the lock protects:** git metadata mutation (worktree add/remove).

**What it does NOT protect:**
- Concurrent `git clone` to the repo cache (no lock around `_ensure_main_repo`)
- Concurrent `git fetch` to update the bare clone
- Shared worktree directory cleanup between policies

**Current jobs=1 behavior:** Lock is effectively unused (single process, serial).
The lock design is correct in principle but has not been stress-tested with jobs>1
since the worktree crash fixes in 012.

**Known gap:** When jobs>1 with same-repo tasks, two policies could concurrently
call `_ensure_main_repo()` (git clone/fetch) without coordination. The file lock
only covers worktree add/remove, not repo cache initialization.

## What Must Happen Before jobs>1

1. **Move repo cache to `/tmp`** — enables safe concurrent clone/fetch without NFS
2. **Move trace scratch to `/tmp`** — removes per-turn NFS writes
3. **Add lock around repo cache mutation** — `_ensure_main_repo` clone/fetch must
   be serialized per repo
4. **Fix mini-swe-agent symlink** — replace with proper submodule or pip install
5. **Add `.gitignore`** — exclude `data/repo_cache/`, `data/runs/`, trace dirs
6. **Stress-test jobs=2 with same-repo tasks** — verify no missing-but-locked,
   no orphan worktree, no stale heartbeat
