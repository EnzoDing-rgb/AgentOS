BudgetFlow Claim 1 — Related Work Boundary

Consolidated 2026-06-30 from the 2026-06-29 boundary table and engineering-system audit. The 2026-06-29 comparison table remains the anchor when older notes disagree.

Vocabulary

shared hard budget
One fixed dollar cap for ALL tasks combined. Once the money runs out, remaining tasks don't run. Not an average, not per-task, not a soft target.
per-query routing
Each query gets routed to a model independently. No coordination across queries, no shared spending pool.
cascade
Try a cheap model first. If the answer looks bad, escalate to a more expensive model. Repeat until acceptable or out of models.
task value
A pre-registered number saying how important each task is. Only counted if the task is verified resolved. Not estimated after seeing results.
verified result
A binary pass/fail from a ground-truth check (e.g., SWE-bench tests pass). Not a predicted quality score or a human preference rating.
decision unit
What the system decides on each time it acts: one query, one task, one subtask, one tool call, or a whole batch.
budget cap
A hard upper limit on spending. If you hit it, you stop. Not a tradeoff knob you can adjust after seeing results.
Total Resolved Value
BudgetFlow's paper-defined metric: sum of task values for all tasks that pass verification. Not a standard benchmark metric.
soft average cost
A target like "average cost per query should be ≤ $0.05." Individual queries can go over; only the long-run average matters. Not a hard cap.
inverse problem
Minimize cost while keeping quality above a floor. BudgetFlow does the opposite: maximize value while keeping cost under a cap.

Executive Summary

Bottom Line

  • All 6 papers study routing or budget control — but at different scopes. They optimize single queries, single tasks, or single multi-agent runs. None combines: shared hard budget across a fixed batch of tasks, pre-registered task value, verified outcomes, and an auditable budget compiler. BudgetFlow is the first system to put these four properties together.
  • Every paper routes/allocates within one query or one task. None allocates spend across tasks under a shared cap. The decision unit is always individual — never a batch with cross-task tradeoffs.
  • None use task value to weight outcomes. No paper distinguishes "this query matters more than that one." All tasks/queries are weighted equally in the objective.
  • Closest neighbors are RouteLLM (learned router inspiration), RouteNLP (deployment routing with inverse objective), and BAMAS (within-task budget ILP). All three operate in the same broad family — making limited model capacity go further — but optimize different decision scopes.
  • BudgetFlow's contribution is the specific combination, not any single mechanism: fixed batch + shared hard budget + pre-registered task value → verified resolved value. Each individual piece may have precedent; the combination and the resulting allocation problem are new.

BudgetFlow Positioning Snapshot

Claim 1
Under one shared hard budget, BudgetFlow maximizes Total Resolved Value: the sum of pre-registered Task Value over verified resolved tasks. Resolved count remains reported as the standard SWE-bench metric.
Claim 2
The mechanism claim: value-aware budget allocation, routing, escalation, stop-loss, and learning explain Claim 1. Routing savings matter only if they protect or improve Claim 1.
Budget Compiler
Pre-run layer. Given task set, ValueSource, model catalog, estimated token demand, and calibration evidence, it compiles the shared cap and planned task budgets before paid execution.
BudgetFlow Runtime
Run-time layer. It allocates model opportunities under the shared ledger, clips each task by remaining budget, records trace/cost/outcome evidence, and stops when the cap is exhausted.
Frontier Matrix
The paper should report when BudgetFlow has value: tight vs loose budget, strong-model turn efficiency, cheap-model short-path wins, learned-router strength, KV-cache cost shifts, and gap to observed-tier frontier.
Generalization Claim
SWE-bench is the verifiable stress test. The portable claim is the governance abstraction: fixed workload, shared budget, value source, cost source, model-fit evidence, and auditable allocation.

BudgetFlow's First-Paragraph Positioning

  • Do not claim "we invented routing" or "same budget, more capability" in generic form. OpenSquilla already uses that language. BudgetFlow's sharper claim is: same fixed task batch, one shared hard budget, pre-registered task values, verified outcomes, and a policy that allocates scarce model opportunities across tasks.
  • The clean theoretical sentence: BudgetFlow tests whether locally strong per-turn or per-task routing becomes globally suboptimal when tasks compete for one shared budget and have different values.
  • Use resolved count as the benchmark metric and Total Resolved Value as the paper metric. This helps answer the "you invented your own metric" attack: SWE-bench resolved rate stays visible, while Task Value is the additional governance objective.
Note on paper selection: A freshness audit (2026-06-29) recommended replacing FrugalGPT (Chen 2023) with Cascade Routing (Dekoninck et al., ICML 2025 poster) — a stronger cascade paper with SWE-bench eval and formal optimality proofs — and Topaz (Okamoto 2026, CHI Workshop) with BAMAS (Yang et al., AAAI 2026 Oral) — a peer-reviewed budget-constrained system with real code-gen experiments. Both original papers are valid Related Work prose citations but weaker comparison-table entries.

Engineering-System Addendum: OpenSquilla / Claw-SWE-Bench

  • OpenSquilla is a serious practical neighbor, not a throwaway comparison. Its README tagline is "Same budget, more capability, better results," and the product guide frames the system around cost-per-success and long-running usefulness. That collides with a weak BudgetFlow pitch. The distinction must be made in the abstract, not buried in Related Work.
  • OpenSquilla's mechanism is stronger than plain model routing. Its router selects configured model tiers, can affect reasoning level and response policy, and is paired with tool compression, cache-continuity safeguards, diagnostics, replay, durable sessions, MetaSkills, scheduling, and per-turn/per-session cost rollups. BudgetFlow should not pretend these are unsolved at the per-turn runtime layer.
  • OpenSquilla still does not appear to solve Claim 1. The public primary docs show per-turn routing inside long sessions and reusable/scheduled workflows, but I did not find evidence of a shared hard dollar ledger across a fixed batch, pre-registered heterogeneous task values, or a policy that optimizes verified Total Resolved Value across competing tasks.
  • Claw-SWE-Bench is methodological convergence, not just hygiene pressure. Its paper explicitly argues for resolved rate plus end-to-end cost under a fixed outer budget and shows a resolve-rate/cost Pareto frontier. Its README also describes a Lite subset selected by a cost-aware, rank-aware procedure. It already shares our evaluation instinct: accuracy alone is not enough.
  • The remaining BudgetFlow gap is allocation, not reporting. Claw-SWE-Bench evaluates harness/model combinations under a common protocol; BudgetFlow decides which tasks receive scarce model opportunities under one shared budget and value matrix. This is the boundary to defend.

What This Changes for BudgetFlow

  • Presentation must become more precise. OpenSquilla already owns a broad "same budget, more capability" story. BudgetFlow should lead with the stricter object: a fixed task batch, one shared hard budget, pre-registered task values, verified outcomes, and cross-task allocation.
  • Evaluation must treat cost/cache as paper evidence. Claw-SWE-Bench and OpenSquilla make cost, usage, cache, and replay visible. BudgetFlow's Claim 1 matrix should report resolved count, Total Resolved Value, spend, value per dollar, execution coverage, KV-cache sensitivity, budget-cap sensitivity, value-profile sensitivity, and frontier gap.
  • Hygiene should be focused on contamination paths that can change pass/fail. Runner-side workspace diff should remain the scoring patch source; submitted patches are audit artifacts. Leakage/future-fix checks matter when agents can read historical reports, gold patches, answer-key fields, or future commits.
  • The strongest future ablation is still compositional: run a SquillaRouter-style local router outside BudgetFlow, then the same router inside BudgetFlow's shared ledger and value allocation. That directly tests whether locally good routing is globally suboptimal under one shared hard budget.
  • LiteLLM/OpenHands are useful because they clarify layers. LiteLLM is enforcement infrastructure; OpenHands is a strong executor with per-task caps. BudgetFlow's claim lives above both: it decides where the shared budget should flow.

Recommended Framing for BudgetFlow Paper

  • RouteLLM-inspired learned task router is the strongest Claim 1 baseline, but the original RouteLLM paper does not have a shared budget, task value, or verified outcomes. The baseline adapts the architecture (classifier trained on task features → pass/fail labels), not the original training objective. Frame it as "RouteLLM-inspired" with explicit disclosure of three adaptation gaps: Chatbot Arena preference data → SWE-bench task success data, single-turn queries → multi-turn agent tasks, uniform query weight → value-oblivious by design.
  • Cascade Routing (ICML 2025 poster) replaces FrugalGPT as the canonical cascade paper. It has formal optimality proofs, SWE-bench evaluation, and a stronger venue. But it remains per-query with expected-cost constraints — no shared budget, no task value. Position it as the state of the art in per-query cost-quality routing, then contrast with BudgetFlow's batch-level value maximization.
  • RouteNLP is the deployment-level neighbor with an inverse objective. It proves that industrial routing at scale (~5K queries/day) works. But it minimizes cost subject to quality ≥ τ, while BudgetFlow maximizes value subject to cost ≤ B. This is the cleanest "we solve the opposite problem" framing in the paper. RouteNLP's conformal cascading and distillation co-optimization are orthogonal techniques that could complement BudgetFlow's shared-budget allocation in future work.
  • BAMAS (AAAI 2026 Oral) is the closest budget-constrained neighbor but within-task, not cross-task. Its ILP + offline RL formulation for LLM selection under a per-task budget is impressive (86% cost reduction on code gen), but it allocates budget to agent roles inside one task, not to tasks inside a batch. This is a crisp boundary: BAMAS handles within-task architecture design; BudgetFlow handles cross-task budget governance.
  • UCCI is a calibration mechanism, not a policy. Its isotonic regression on token margins (ECE 0.12 → 0.03) is valuable methodology for BudgetFlow's Model Fit estimation. Position it in Claim 2 mechanism discussion, not Claim 1 baselines. The right question is "does better Model Fit calibration improve BudgetFlow's allocation decisions?" not "does UCCI beat BudgetFlow?"
  • INTENT studies within-task tool-call planning under a per-task budget; BudgetFlow studies cross-task model-tier allocation under a shared budget. These are complementary decision layers. The paper should add one sentence: "INTENT manages which tools to call and when to stop inside one task; BudgetFlow manages which tasks get scarce model opportunities inside one budget." INTENT's learned world model and intention predictor could theoretically serve as the inner executor within BudgetFlow's outer allocation loop.
  • BudgetFlow's core distinction is irreplaceable: fixed batch + shared hard budget + pre-registered task value + verified resolved value. Zero of the 6 papers combine these four. The paper's novelty argument should center on this combination, not on individual mechanism components (routing, calibration, or tool planning).
  • Use the "inverse problem" framing consistently. RouteNLP, UCCI, and Cascade Routing all solve min cost s.t. quality ≥ τ. BudgetFlow solves max value s.t. cost ≤ B. The inverse framing is intuitive, memorable, and makes the problem-class distinction clear to reviewers without requiring them to read code or trace experiments.

Papers Considered but Not in Main Table

FrugalGPT (Chen et al., 2023): Pioneered LLM cascading (700+ citations), but its soft average budget E[cost] ≤ b and DistilBERT answer-quality scorer make it a weaker cascade representative than Cascade Routing (ICML 2025 poster), which adds formal optimality proofs and SWE-bench evaluation. Mention in prose as the first LLM cascade paper, then pivot to Cascade Routing for current state of the art.

Topaz (Okamoto et al., 2026, CHI Workshop): Moves to prose-only because BAMAS (AAAI 2026 Oral) provides a stronger empirical budget-constrained system for the main table. However, Topaz remains important to BudgetFlow's story: its skill-based explainable routing and structured audit traces are directly relevant to BudgetFlow's transparency and auditability goals. The 8-skill taxonomy and trace-driven explanation approach should be cited in the explainable AI / transparent orchestration section of Related Work. The appendix DP formulation (budget-based mode) is a textbook knapsack — not a novel contribution — but the idea of budget-constrained task-to-model assignment under an auditable plan aligns with BudgetFlow's compiler design.

Additional prose-only citations: ZEBRA (Hamri & Talgam-Cohen, 2026) — zero-shot budget splitting supports the premise that structured allocation beats LLM-direct. Triage (Madeyski, 2025) — SWE-bench-specific routing with code health signals, preliminary. Varangot-Reille et al. (2025) — comprehensive routing taxonomy survey; cite once to position BudgetFlow. HybridLLM (Ding et al., ICLR 2024) — early ICLR router, superseded by RouteLLM. RouterBench (Hu et al., 2024) — standard routing benchmark.
