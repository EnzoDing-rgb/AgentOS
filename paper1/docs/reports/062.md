# 062 — Auto-Budget Learning Gate and Fresh 3x3 Validation

**Date:** 2026-06-06
**Status:** COMPLETE
**Branch:** `main`

## Executive Summary

062 tested the post-061 Value-Driven Budget Allocation loop end to end:

- fixed a learning bug where `not_enough_evidence` rows could pollute learned cap medians;
- added a zero-API `--auto-budget-dry-run` cap audit gate;
- ran a fresh 3 policies x 3 tasks paid validation with learned per-task caps and one Django task.

BFV gives a real Tier 1 positive signal: it is the only strategy to solve all 3 tasks and doubles resolved value versus BO. But Tier 2 is not supported in this run: BFC costs more and uses more turns than BO. The largest remaining runtime bug is submit/evaluate timing after a gold-file edit. Multiple policies edit the right file, then spend 5-18 extra turns before fallback evaluation.

## Infra Fixes

### 1. Weak evidence excluded from budget learning

Root cause: `AutoBudgetEstimator` treated every non-harness/non-corrupt memory row as usable. That included 1-step smoke rows with `cap_was_sufficient=not_enough_evidence` and very low cost, which could lower future caps incorrectly.

Fix: memory estimates now use only:

- `sufficient`
- `likely_underbudget`
- `underbudget_or_model`

Regression tests:

- `test_not_enough_evidence_excluded_from_exact_memory`
- `test_not_enough_evidence_does_not_lower_successful_memory`

### 2. Auto-budget dry-run gate

Added:

```bash
python -m budgetflow.run_mini_swe_compare --auto-budget-dry-run ...
```

This prints cap estimates, source, confidence, and neighbor count without provider checks or run artifacts.

### 3. Dynamic-cap summary bug

Raw JSONL rows were correct, but summary tables treated `--auto-budget`'s `per_task_cap=-1.0` sentinel as shared-budget mode and displayed `batch_cap=100.00`.

Fix: summary mode now distinguishes:

- `per_task_cap`: fixed cap multiplied by completed rows;
- `dynamic_task_caps`: learned caps summed once as planned cap;
- `shared`: shared batch cap.

Historical JSONL and summary files were not edited.

## Claim Readout

### Tier 1: Positive, but not headline-ready

BFV solves all tasks and recovers the two high-value tasks. It doubles BO's resolved value:

- BFV: 0.6610
- BO: 0.3320

This supports the direction of Value-Driven Budget Allocation: learned caps and task-wise value can preserve work on valuable tasks that a simpler baseline drops.

Caveat: BFV's RVPD is slightly below BO in this run (1.430 vs 1.474) because BFV spends more to solve the extra high-value task. That is acceptable for the North Star only if the paper emphasizes resolved value under budget and value-token tradeoff, not only per-task cost.

### Tier 2: Not supported in this run

BFC is value-blind and should test routing efficiency. It does not look efficient here:

- cost: BFC $0.4463 vs BO $0.2253
- turns: BFC 65 vs BO 26
- pass: both 2/3

BFC solves `sympy__sympy-16988`, so it has rescue ability, but its cost and turn count are too high. This is not a clean routing-efficiency win.

## Runtime Findings

### Gold-edit fallback works

Several rows did not submit a patch, but local worktree diff was extracted and evaluated. This is valuable engineering behavior because it converts protocol failures into usable patches.

Examples:

- BFV `sympy__sympy-16988`: PASS via `StagnationExit`, worktree diff.
- BFV `django__django-10924`: PASS via `StagnationExit`, worktree diff.
- BO `django__django-10924`: PASS via `StagnationExit`, worktree diff.

### Gold-edit timeout is too slow

After first repair/gold-edit signal, policies often keep spending turns before fallback evaluation:

| Row | First Repair | Total Turns | Post-Repair Turns |
|---|---:|---:|---:|
| BFC sympy__sympy-16988 | 13 | 31 | 18 |
| BFV django__django-10924 | 8 | 19 | 11 |
| BFC django__django-10924 | 9 | 21 | 12 |
| BFV sympy__sympy-16988 | 16 | 21 | 5 |

The current `rescue_timeout_gold_edited evidence_turns=10` eventually stops the loop, but too late. This directly hurts Tier 2 cost efficiency and can mask BFV's value allocation benefits.

## Next Judgment

Do not scale to 3x5/3x8 yet.

Next P0 is runtime intelligence:

1. tighten gold-edit fallback/evaluation timing;
2. distinguish "patch exists, evaluate now" from "keep asking the model to repair";
3. preserve the current worktree-diff fallback because it rescued valid patches;
4. rerun the same 062 3x3 after the fix before adding more tasks.

Only after this stabilizes should we expand task types or run a larger batch.
