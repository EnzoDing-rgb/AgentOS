## Task A: Evidence Hardening

### Changes to `scripts/autoresearch_api_worker.py`

Three additions:

1. **`worker_metadata.json` sidecar** — written alongside `worker_output.md` in the same attempt directory. Contains:
   - `model` — actual model used
   - `input_tokens`, `output_tokens` — from API response
   - `status_code` — HTTP status
   - `timestamp_utc` — when the call was made
   - `output_path` — where output was written
   - `marker_present_in_model_output` — did the model output contain PASS marker?
   - `marker_appended_by_wrapper` — did the wrapper need to append it?
   - `error` — error message if call failed, null on success

2. **Factual header** — prepended to every `worker_output.md`:
   ```
   <!-- AutoResearch API Worker — factual metadata
     model: deepseek-v4-flash
     input_tokens: 4887
     output_tokens: 808
     metadata: worker_metadata.json
   -->
   ```
   This makes the script-level truth visible alongside the LLM-generated content.

3. **Error-path metadata** — metadata is written even on HTTP errors or
   connection failures, capturing `status_code` and `error` fields.

## Task B: Goal-Level Coordinator

### New module: `src/budgetflow/autoresearch_goal.py`

**Goal dataclass:**
- `goal_id`, `title`, `status` (pending|running|paused|complete|failed)
- `issue_ids` — ordered list of issue IDs
- `current_issue_index` — cursor tracking progress through the issue list
- `max_retries_per_issue` — default 2
- `real_api_budget_cap_usd` — budget guard
- Serialized to `.autoresearch/goals/<goal_id>.json`

**GoalManager:**
- `create_goal()` / `load_goal()` / `add_issue()`
- `run_goal()` — finds the next pending/failed issue, calls coordinator.run(), advances cursor
- `print_goal_status()` — table of issues with status, attempts, pause reasons
- `write_goal_summary()` — generates `.summary.md` with verdicts table

### New CLI Commands in `run_autoresearch.py`

| Command | Purpose |
|---------|---------|
| `goal-create --goal-id ID --title TEXT --budget-cap-usd FLOAT` | Create a new Goal |
| `goal-add-issue --goal-id ID --issue-id ISSUE` | Add an issue to a Goal |
| `goal-status --goal-id ID` | Show Goal status with per-issue breakdown |
| `goal-run --goal-id ID [--dry-run\|--manual\|--worker-cmd CMD] [pause flags]` | Run one step of the Goal |

`goal-run` behavior:
- Finds the first pending/failed issue starting from `current_issue_index`
- Invokes coordinator.run() for that issue
- If issue failed and attempts <= max_retries: stays on same issue for retry
- If issue complete: advances cursor to next issue
- If all issues complete: goal status → complete
- If pause condition triggers: goal status → paused

## Review Fix (Phase J — 040)

Phase J review identified the following evidence inconsistencies from the
original Phase I delivery. These were fixed in Phase J.

### Issues Found

1. **summary.md status ≠ JSON status** — `summary.md` showed `Status: running`
   while `goal JSON` had `status: complete`. Root cause: `write_goal_summary()`
   wrote a stale status string from the in-memory Goal object before
   `_write_goal()` updated the JSON. Fix: `write_goal_summary()` now reloads
   the goal from disk before writing.

2. **total_api_calls = 0** — The field was never incremented because
   `GoalManager.run_goal()` has no visibility into whether the worker made a
   real API call (fake workers don't). Fix: added `_aggregate_goal_metadata()`
   that scans all `worker_metadata.json` sidecars across all issues and
   computes live counts for `total_api_calls`, `total_input_tokens`,
   `total_output_tokens`, `marker_appended_count`, and `successful_http_calls`.
   The aggregated values are written back to goal JSON and summary on every
   `write_goal_summary()` call.

3. **write_goal_summary() stale data** — Previously read `goal.total_api_calls`
   from the in-memory Goal object, which was always 0 on first load. Fix:
   aggregates from disk every invocation and updates goal JSON.

### After Fix

|-------|--------|-------|

## Remaining Gaps

1. **Codex automatic review** — `codex_review_fn` callback exists but Codex
   review is still manual. The thin API worker could be used as a reviewer
   with a different system prompt. This is the next logical step to close
   the last manual step in the inner loop.

2. **Post-gate auto commit/push** — after Codex approves an issue, the
   accepted changes should be committed and pushed automatically. Deferred
   until Codex gate reliability is proven.

3. **Owner approval resume UX** — when a Goal hits a pause condition (e.g.,
   paid 3x10), the owner needs to explicitly approve or deny. Currently
   the Goal stays paused until the owner manually overrides. A `goal-resume`
   command would improve the UX.

4. **Real Claude Code worker adapter** — the thin API worker calls the
   Anthropic Messages API directly. For tasks that require file editing
   (not just read-and-summarize), a real Claude Code worker adapter would
   need the tool-use loop. The worker bridge already supports any shell
   command, so this is a deployment concern.

5. **Goal dependency ordering** — issues run sequentially in list order.
   No support for "issue B depends on issue A" or parallel issue execution.
   The `autoresearch_workflow.md` design reserves this for future work.
