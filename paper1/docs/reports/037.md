## Root Cause Analysis

`claude -p` spawns a full Claude Code session. Even with `--bare` (minimal
system prompt, no CLAUDE.md loading, no hooks), the session overhead includes:

1. Tool schema definitions (Read, Write) — several hundred tokens
2. System prompt with behavioral rules — thousands of tokens
3. Environment context injection — hundreds of tokens
4. The actual user instruction

The token overhead (~10K+ input tokens before the Worker even reads its
prompt) consumes the budget on session setup alone. For comparison, a raw
API call to the Anthropic endpoint with a minimal system prompt + user
message would use ~2K input tokens total.

## Does AutoResearch Support Real Worker Bridge?

**Yes — the bridge infrastructure works.** The coordinator + CLI correctly:
- Created workflow state on disk
- Invoked the Worker via `--worker-cmd` with prompt/output path substitution
- Tracked attempts (1 → 2 → retry exhausted)
- Preserved state for inspection

What's missing is a **thin enough Worker adapter** that fits within the budget.
The `claude -p` CLI has too much session overhead. A raw API wrapper would
solve this without any changes to AutoResearch itself.

## Recommended Path Forward

Three options (in order of feasibility):

1. **Thin API worker** (`scripts/autoresearch_api_worker.py`) — use `curl` or
   `requests` to call the Anthropic Messages API directly with a minimal system
   prompt. Estimated token usage: ~2K input, ~500 output. Should fit within
   $0.05 even on expensive models.

2. **Pre-canned output** — for this specific smoke (read 2 files, write
   structured summary), accept the fake worker result as sufficient evidence
   that the AutoResearch bridge works. Phase D smoke already proved the full
   loop. The remaining variable is the Worker adapter, which is a deployment
   concern, not a coordinator/CLI concern.

3. **Lower-cost model** — check if a cheaper model (e.g., DeepSeek flash via
   `ANTHROPIC_SMALL_FAST_MODEL`) would fit the budget for `claude -p`.

## Residual Risks

1. **Budget opacity** — `claude -p` reports "exceeded budget" but doesn't
   show how much was actually consumed. Actual spend could be anywhere from
   $0 to $0.50 per attempt. A thin API wrapper would give precise cost tracking.

2. **Worker CLI availability** — `claude -p` is the only non-interactive
   Worker CLI discovered. If it's always too expensive for small tasks,
   AutoResearch needs its own thin API adapter to be practically useful.

3. **No real Worker output** — the smoke did not produce a worker_output.md
   from a real agent, so we haven't verified end-to-end artifact quality
   with a real LLM. This is a budget constraint, not an architectural one.
