## 2. 027 Experiment Design

### Purpose
Verify BudgetMemory generalization in a real experiment with `--budget-memory-exclude-ids` — forcing cascade tiers (no exact_task memorization).

### Command

```
PYTHONPATH=src:../external/mini-swe-agent/src python -u -m budgetflow.run_mini_swe_compare \
  --ids django__django-10924,sympy__sympy-13480,sympy__sympy-13647,sympy__sympy-14774,sympy__sympy-16988 \
  --strategies budget_tight_smart,budgetflow_tight \
  --budget-memory data/runs/postfix_017_10x5-0.jsonl,...,postfix_024_bm_10x2_repeat.jsonl \
  --budget-memory-exclude-ids django__django-10924,...,sympy__sympy-16988 \
  --run-series postfix_027_loo_bm_5x2 \
  --out-stem postfix_027_loo_bm_5x2 \
  --jobs 1 \
  --trace-turns \
  --resume
```

### Design

- 5 tasks × 2 strategies = 10 runs, --jobs 1 (serial)
- BudgetMemory trained on 017/018/021-024 with 5 current tasks excluded
- Training set after exclusion: 70 records, 5 tasks (sympy__sympy-17630, -18057, -18189, -18621, -20212), 1 repo (sympy)
- Total runtime: 23 minutes

### 3.4 Why strategy_median not repo_median

BudgetMemory builds repo keys from `instance_id.split("__")[0]` (e.g., "sympy"), but the runner passes the SWE-bench Mini repo slug (e.g., "sympy__sympy") to `estimate_task_budget()`. This key mismatch causes repo_median lookup to miss, falling through to strategy_median.

After exclusion, sympy repo has 70 records — enough for repo_median tier (≥ 3 threshold). Django repo has 0 records — correctly falls to strategy_median.

This is a repo-key normalization bug, not a cascade logic bug. The estimates from strategy_median are still reasonable: $0.1514 median for `budget_only_tight` across 20 records.

**Does this invalidate the LOO result?** No. The core claim is "0% exact_task leakage" — and that holds regardless. The cascade DOES use higher tiers (strategy_median), just not the optimal one. Fixing the repo-key normalization would make estimates more accurate for sympy tasks (repo_median: $0.2120 vs strategy_median: $0.1514).

## 6. Should We Continue to Larger Scale?

**Not yet.** The 10-task LOO validation (026 Gate A) showed 1/10 severe_underbudget and 2/10 overbudget from repo_median. But 027 didn't exercise repo_median due to the repo-key normalization bug.

**Pre-conditions for 15/20-task LOO experiment:**
1. Fix repo-key normalization so cascade hits repo_median for multi-task repos
2. Re-run LOO offline validation after fix to verify improved accuracy
3. 027 at 5×2 showed LOO experiment infrastructure works (0% exact_task, gate clean, no hangs)

**Current state:** BudgetMemory LOO infrastructure is working. The cascade correctly avoids exact_task when exclude_ids are set. The repo-key fix is a one-line change that would improve estimation accuracy for multi-task repos.
