# 025 — P0: Zero-progress hang detection & heartbeat fix

## 1. Root cause

**Thread-pool worktree deadlock with `--jobs 3` on shared repo.**

`HeartbeatWriter` set `status="running"` at construction (before any task submission), and `_beat()` fired every 30s inside `run_with_heartbeat` without passing `active_elapsed_s`. With 3 strategies all targeting `django__django-10924` first, 3 `ThreadPoolExecutor` threads contended for the same `_repo_git_lock()` (fcntl.flock). One held the lock doing NFS git worktree ops; the other 2 blocked on flock. The heartbeat daemon threads kept updating `updated_at` every 30s, masking the prep-block as "fresh heartbeat." The checker's `_rows_stuck()` only flagged stale heartbeats — fresh ones with zero progress passed as OK.

**Evidence:** 025 ran 6h42m, 0 JSONL rows, heartbeat `updated_at` was 6.7h after `started_at` but `active_elapsed_s=0.0`. No `[route]`, `[agent]`, or `[prep_step]` lines — only `[heartbeat]` pulses.

## 5. Fixes applied

### 5.1 HeartbeatWriter initial status (observability.py)
- `status="running"` → `status="preparing"` at construction.
- Tasks now transition from "preparing" to active only when `pulse()` is called with a real `active_strategy`.

### 5.2 `_beat()` passes `active_elapsed_s` (run_mini_swe_compare.py)
- `_beat()` now tracks `_task_started` timestamp and passes `active_elapsed_s=time.time() - _task_started`.
- Previously `active_elapsed_s` was always 0 during execution (only set at completion by `_on_task`).

### 5.3 Zero-progress stuck detection (check_run_observability.py)
- `_rows_stuck()` now detects 3 zero-progress scenarios even with fresh heartbeat:
  1. `rows_done=0 + elapsed > threshold + active_elapsed_s=0` → stuck in prep
  2. `rows_done=0 + active_elapsed_s > threshold` → single task stuck too long
  3. `rows_done=0 + elapsed > threshold + no active task` → setup/thread pool blocked
- Heartbeat check now scans `*.heartbeat.json` files even when JSONL has 0 rows (previously skipped when `run_series_set` was empty).

### 5.4 Checker output for 025 after fix

## 7. North Star impact

### Impact on shared budget account
This bug violates the core semantic of a shared budget ledger:
- Runner claimed "running" with 3 active tasks consuming budget/window time, but 0 real progress.
- The budget account with no visibility into whether resources were actually being used.
- `active_elapsed_s=0` in heartbeat meant the governor couldn't distinguish between "making progress" and "blocked on infra."
- Checker's "all OK" signal would lead a human to trust a dead run for hours.

### How the fix improves reliability
1. **Status transparency:** `preparing` → `active` → `completed` lifecycle is now observable. A run stuck in `preparing` for 10+ minutes is flagged.
2. **Zero-progress detection:** Even with fresh heartbeat pulses, the checker now distinguishes liveness (heartbeat daemon alive) from progress (rows or active_elapsed_s advancing).
3. **Resume/stop safety:** An operator can now trust the checker's `HEARTBEAT_STUCK` signal to kill and resume, rather than discovering 0 rows 6 hours later.
4. **Budget accounting integrity:** `active_elapsed_s` now tracks real task wall-clock time during execution, not just at completion. Future governors can use this to bound budget windows.

### Enterprise runtime relevance
Beyond SWE-bench:
- A multi-tenant budget orchestrator must not silently burn budget tokens on stuck workers.
- Heartbeat freshness ≠ task liveness — this distinction applies to any async job system (Kubernetes, Celery, etc.).
- The fix pattern (heartbeat track prep vs execution, zero-progress detection) transfers to any system where a sidecar thread reports "alive" while the work thread is blocked.

## 8. Recommendations

### Rerun dummy diagnostic?
No. The dummy strategy (`all_flash` routing, T1 only, no escalation) takes >300s for one task and requires 3 jobs with worktree contention. Not worth the cost. The probe proved it works in isolation.

### Run 15/20 task tomorrow?
**No, unless:**
1. The model_fail bottleneck is addressed (13/28 failures are model, not budget). More tasks won't change this.
2. `--jobs` is fixed to not deadlock with 3+ strategies on NFS. Options: per-repo semaphore instead of flock, or sequential prep phase.
3. If running anyway: repeat 10×2 with 3-5 different random seeds/orders rather than scaling to 15 tasks. Statistical variance at n=10 is the primary bottleneck, not task count.
