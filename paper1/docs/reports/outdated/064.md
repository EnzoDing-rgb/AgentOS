**Date:** 2026-06-06
**Status:** COMPLETE

## Summary

064 tested the anti-spin fix from `7cde0e3` on the same 3-task gate used by 062/062b.

The result is negative for both claims.

It is still useful: it proves that simple no-progress early stopping saves money but is too blunt for BudgetFlow.

## Code Fixes Before the Run

### Repair phase no longer implies progress

Root cause from 062b: the runtime treated agent `edit_gold` / repair phase as progress even when the actual command was read-only. This let BFV/BFC spend many turns inspecting files or rewriting temporary artifacts while anti-spin counters stayed at zero.

Fix:

- added `command_counts_as_progress()`;
- read-only commands inside repair phase no longer reset stagnation;
- validation phase still counts as progress;
- `STAGNATION_NO_PROGRESS_STEPS` changed from 40 to 12.

Regression tests:

- `test_read_only_command_in_repair_phase_does_not_reset_stagnation`
- `test_real_repair_command_counts_as_progress_even_without_phase`
- `test_validation_phase_counts_as_progress_for_stop_loss`

### Stagnation without patch is not budget failure

064 exposed a classifier bug: BFC/BFV no-patch `stagnation_no_progress` rows were stored as `budget_fail/conservation_lockout`. That was wrong because the runs still had budget available and had already received some T3 access.

Fix:

- conservation lockout now requires trace evidence of max-tier/conservation gating and no T3 access;
- no-patch stagnation is classified as localization/model behavior failure.

Historical JSONL was not edited. The checker reports stale verdict fields for affected 064 rows and recomputes the current verdict.

## Claim Readout

### Tier 1

Not supported.

BFV solved only the low-value task. It failed both high-value tasks via no-patch stagnation before producing a repair.

The value-aware multiplier alone is not enough. The runtime needs a better salvage policy when a high-value task stalls before patch generation.

### Tier 2

Not supported.

BFC solved only 1/3 and spent more than BO. It also spent 31 turns on Django before producing a failing worktree patch.

The routing mechanism currently saves some cost by stopping earlier, but that is not routing efficiency if it loses solvable tasks.

## Interpretation

The anti-spin fix moved the system in the right engineering direction but exposed a missing policy layer:

```text
stalled before patch
  -> if low value / low budget: stop
  -> if high value and budget remains: force salvage action or stronger model
```

Today the runtime mostly chooses the first branch. That is why BFV underperforms exactly where Tier 1 should help.

## Next Judgment

Do not scale to 3x5 or 3x8 yet.

Next P0 is to replace blunt stagnation stop with value-aware salvage:

- no-patch localization stagnation on high-value tasks should trigger a bounded T3 salvage window, not immediate stop;
- after a gold-file edit, repeated repair without harness improvement should evaluate or stop sooner;
- BFC should remain value-blind, but BFV should use task value in stop/continue decisions.

After that fix, rerun a 3x3 gate before adding new tasks.
