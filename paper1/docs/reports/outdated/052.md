## 1. Executive Summary

Phase V investigated **why BudgetFlow lost to BudgetOnly in the 051 value-stress experiment** (BF 3/5 PASS, BO 4/5 PASS, SB 4/5 PASS). Two root causes were identified and fixed with code + tests. A third issue (experiment design) was documented for future correction. Paid validation is blocked by missing API keys.

**Root causes found and fixed:**
1. **False baseline**: `BudgetOnlyStepRouter` uses T3 when `budget_pressure < 0.15`, making it a strong pressure-router, not a "dumb" cost-only baseline.
2. **Inverted pressure direction**: `BudgetFlowSelector` escalates T3 as pressure rises (correct for no-progress streaks, wrong for budget depletion — should become MORE conservative, not MORE aggressive).

**Fix**: Added `BudgetOnlyT2Router` (true cost-only baseline, never escalates) and `ConservativeSelector` (makes T3 escalation harder as budget depletes). Both are registered as new strategies.

**Tests**: 12/12 passing (`test_phase_v_fixes.py`). Core test suite: 129/129 passing.

## 2. First-Principles Invariant

**North Star**: BudgetFlow optimizes for *verified resolved value per dollar under a hard shared budget pool*. It is NOT a claim that BF is always cheaper than a cost-only baseline.

**What BF should dominate**:
- Value allocation: given a fixed shared budget, BF should allocate more resources to higher-value tasks than a dumb baseline
- Cost efficiency: on commonly-solved tasks, BF should have lower or equal cost (Second Claim)
- Per-task budget discipline: BF should not waste budget on unsolvable tasks

**What BF does NOT promise**:
- To solve every task a best-model strategy solves
- To beat an unconstrained T3 strategy on pass rate
- To be cheaper than a hand-tuned workflow-level router on every individual task

**What 051 tested vs what it should have tested**:
- 051 used shared batch cap ($0.50/5 tasks), which confounds task ordering with policy ability
- BO solved 4/5 with the first 4 tasks benefiting from fresh budget; task 5 got $0.00 and auto-failed
- This created a false impression that BO is "cheaper and more effective"

### 3.2 Hypothesis Testing

| Hypothesis | Verdict | Evidence |
|---|---|---|
| BO is a true cost-only baseline | **FALSE** | BO used 6% T3 turns (5/84). At pressure<0.15, BO picks T3. |
| BF uses more T3 than BO | TRUE | BF 33% vs BO 6% |
| BF's T3 use is productive | **FALSE** | BF 54% T3 on sympy-16988 and still FAILED |
| Shared batch cap confounds results | TRUE | Task 5 got $0.00 budget in BO batch |
| BF's pressure direction is correct for budget conservation | **FALSE** | Pressure rises → easier T3 escalation → burns remaining budget |

### 3.3 Root Cause Verdict

**Primary**: `BudgetFlowSelector` has inverted pressure semantics. Higher pressure (depleted budget) → lower upgrade threshold → easier T3 escalation. This is correct for the "no-progress streak" signal but WRONG for the "budget running out" signal. As budget depletes, the router becomes MORE aggressive, burning expensive T3 when money is tightest.

**Secondary**: `BudgetOnlyStepRouter` is a misleading baseline name. It's not a "dumb cost-only" router — it's a pressure-gated router that uses T3 when budget is plentiful.

**Tertiary (experiment design)**: Shared batch cap ($0.50 for 5 tasks) with fixed task ordering creates a systematic evaluation bias. Early tasks get fresh budget; later tasks starve. With BO, the first 4 tasks solved with $0.50 — task 5 got $0.00. With BF, budget was spread but less effectively.

## 4. Code Changes

### 4.1 `policies.py` — BudgetOnlyT2Router (+45 lines)
True cost-only baseline. Always picks cheapest tier (T1 in 3-tier pool, T2 in 2-tier pool). Never escalates regardless of pressure.

```python
class BudgetOnlyT2Router:
    """True cost-only baseline: always picks cheapest available tier (T2)."""
    def choose_backend(self, turn_info, backends, budget_pressure):
        ordered = sorted(backends, key=lambda b: b.tier)
        return RouterDecision(
            backend=ordered[0], reason="t2_only_baseline",
            pressure=budget_pressure, branch="budget_only_t2",
        )
```

### 4.2 `selector.py` — ConservativeSelector (+54 lines)
BudgetFlowSelector variant with conservation pressure. Multiplies upgrade threshold by `1.0 + max(0, pressure - 0.3) * 3.0`, making T3 escalation progressively harder as budget depletes.

- At p=0.3: factor=1.0 (no change)
- At p=1.0: factor≈3.1 (T3 ≈3× harder)

### 4.3 Integration points updated (8 files)
