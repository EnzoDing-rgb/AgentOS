## Part B — Value Observability (COMPLETE)

### B.1 Row-Level Fields

`_enrich_record_with_value()` injects 6 fields into each run record before JSONL write:

| Field | Description |
|---|---|
| `task_value_profile` | Which value profile was used (default: `equal`) |
| `task_value` | The value weight assigned to this task |
| `resolved_value` | `task_value` if resolved, else `0.0` |
| `value_source` | `value_matrix` or `default_equal` |
| `value_matrix_artifact` | Path to the value matrix JSON, or `null` |
| `yield_per_dollar` | `resolved_value / task_cost` (0 if cost=0) |

### B.2 CLI Flags

```
--value-profile {equal,difficulty,discriminative_rarity,unsolved_difficulty,combined}
--value-matrix PATH
```

Both default to equal profile (all tasks=1.0) when omitted. `_init_value_observability()` is
called once in `main()` after args parse.

### B.3 Summary Output

`_value_summary_for_strategy()` computes per-strategy value metrics:
`resolved_count`, `total_cost`, `resolved_value`, `total_task_value`, `yield_per_dollar`.

Live snapshot (`_format_live_snapshot()`) shows a VALUE SUMMARY section with per-strategy
breakdown. Summary JSON includes value fields.

### B.4 Design Decision: Module-Level Globals

Value config is stored in module-level globals (`_VALUE_LOOKUP`, `_VALUE_PROFILE`,
`_VALUE_MATRIX_PATH`) set once at startup. This avoids threading a config object through
every call site. The tradeoff (test isolation) is managed by re-calling
`_init_value_observability()` in each test.
