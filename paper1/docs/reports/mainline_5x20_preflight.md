## Budget binding (target_utilization=0.80)

| Metric | Value |
|---|---|
| budget_mode | target_utilization |
| target_projected_utilization | 0.80 |
| reference_rule | strategy_set_p75_projected_spend |
| p75_reference | $0.9809 (budgetflow_full) |
| hard_cap_usd | $1.2262 (= p75_ref / 0.80) |
| projected spending | T2=$0.7546, T3=$1.5091, enterprise=$0.7546, bf_same=$0.7546, bf_full=$0.9809 |
| utilization | T2=61.5%, T3=100.0%, enterprise=61.5%, bf_same=61.5%, bf_full=80.0% |
| min_viable_budget | $1.5091 (bare_t3_baseline) |
| calibrator decision | PASS |
| catalog | model_tiers.t3x2.json (revision 2026-06-10-t3x2) |

The p75 reference ($0.9809 = budgetflow_full projected spend) is a distribution statistic
across all 5 strategies — not keyed to any single policy. hard_cap = p75_ref / 0.80 =
$1.2262, creating budget pressure where T3 projects at 100% utilization and budgetflow_full
at exactly 80%.

Pressure shape (audit output, never a generation rule):
- T2/enterprise/bf_same at 61.5%: comfortable headroom
- budgetflow_full at 80%: at target utilization
- bare_t3 at 100%: exactly at hard_cap, may not complete (tight_budget_warning)

This is the expected tight-budget signature: cheapest strategies have room, the value-aware
strategy is at target, and the strongest-model baseline is budget-constrained. The budget
is $1.23 — barely enough for the strongest model to attempt all tasks.

## Residual risks

1. **Tight budget ($1.23)**: The target_utilization=0.80 budget is intentionally
   tight. bare_t3_baseline (pure T3, the most expensive strategy) projects at 100%
   utilization — it may not complete all tasks within the shared batch budget.
   This is expected: the budget is designed to reveal which strategies complete
   within a binding constraint. If bare_t3 times out, it confirms that the budget
   is binding enough to differentiate routing-level effects from raw model
   capability.

2. **Zero-history Requests tasks (1963, 3362)**: No prior paid data exists for
   psf/requests in this setup. Bootstrap cost estimates (33.06, 31.47) come from
   SWE-bench metadata formula. First-paid-run variance is expected. RequestsHAdapter
   is no-op — pytest should work out of the box, but repo-specific surprises possible.

3. **Zero-history Sphinx tasks (7975, 10325)**: No prior paid data for sphinx-doc/sphinx.
   Bootstrap estimates (34.43, 33.03). The jinja2 compat adapter is tested for
   idempotency and regex correctness, but first run on this repo version may reveal
   additional compat issues (other deprecated jinja2 APIs, Python version
   incompatibilities).

4. **Gold sanity pending**: The 4 new tasks (requests-1963, requests-3362, sphinx-7975,
   sphinx-10325) have not been gold-sanity-tested. SWE-bench test patch evaluation
   must confirm RESOLVED status before paid experiment. The bootstrap heuristic
   assumes Solvable=True. If any task is Unresolved, the value matrix and frozen
   plan must be regenerated.

5. **t3x2 catalog sensitivity**: The 2x T3 pricing diagnostic catalog amplifies
   the T3 cost signal. The budget is calibrated against this diagnostic catalog.
   If the default (real pricing) catalog is used, T3 projected spend would be
   ~$0.7546 (same as T2), and the p75 reference would drop. The tight-budget
   effect depends on the diagnostic catalog's cost ratio.

6. **4-repo generalization**: First experiment spanning 4 repos. The adapter
   dispatch (`RepoHarnessAdapter.for_task()`) is repo-slug-based, not task-id-based.
   No repo-specific routing exists beyond the adapter layer. But 4-repo diversity
   has not been stress-tested in a paid run.
