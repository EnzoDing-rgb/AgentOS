BudgetFlow Related Work 对比

这份页面的目的：把问题讲清楚，说明别人已经做到了哪一步，我们真正新增的是什么，哪些地方需要更克制地写。已按 primary / official sources 做 2026-07-06 校正。

先说结论

一句话版本

  • OpenSquilla / Claw-SWE-Bench 很强，它们主要强在 agent runtime、评测工艺、cost/cache/trace 可见性和 cost-per-success 叙事。BudgetFlow 的 Claim 1 聚焦跨任务共享预算分配。
  • vLLM / SGLang / NVIDIA Dynamo 说明 agentic inference 已经是重要系统问题。 它们把 batching、prefill、KV/prefix cache、priority scheduling 和 cache-aware routing 做实。BudgetFlow 把 Task Value、shared budget 和 verified outcome 变成预算分配与优先级信号。
  • 现有 routing / cascade / budget papers 大多只管单个 query 或单个 task。 BudgetFlow 处理一批任务共用一个 shared hard budget、任务价值不同、并且最后按 verified outcome 结算总价值的问题。
  • BudgetFlow 的边界要写得更窄、更准。 核心句子是：在固定任务批次下，如何把一个共享硬预算分给不同价值的任务。

先把三层问题分开

single query、single task、shared-budget batch 不是一回事

  • single query：“把这段邮件润色一下。” 系统只需要决定这一次请求用便宜模型还是强模型，然后立刻回答。
  • single task：“修掉这个 Django bug。” 系统要连续做很多步：读 issue、看代码、搜文件、改 patch、跑测试、再修。
  • shared-budget batch：“这里有 30 个 bug，总预算 10 美元，怎么分配？” 系统不只管一个 bug，而是要决定整批任务里谁先拿预算、谁该上 T3、谁该止损。
  • RouteLLM 更像：“这一条 prompt 值不值得上 GPT-4？”
  • INTENT / BAMAS 更像：“这个单独任务内部，下一步要不要调用更贵的工具，或者换更强的 agent？”
  • BudgetFlow 更像：“30 个任务里，哪几个值得先救？预算快没了时，该把 T3 留给谁？”

Level 1: per-query

一次请求进来，系统只需要决定这一次调用用哪个模型，然后马上给答案。

例子：
“把这段邮件润色一下。”
系统只问一件事：这一次要不要上更强模型？

Level 2: per-task

一个完整任务要经过很多步，系统要决定任务内部下一步怎么做，而不是只答一次。

例子：
“修掉这个 Django bug。”
要连续做：读 issue、看代码、改 patch、跑测试、再修。

Level 3: batch of tasks

一批任务共用一笔钱，系统要决定预算先花给谁、谁值得上强模型、谁该及时止损。

例子：
“这里有 30 个 bug，总预算 10 美元。”
真正的问题是：先救谁？谁该上 T3？谁该放弃？

OpenSquilla / Claw-SWE-Bench 对我们意味着什么

它们把边界逼清楚了

  • OpenSquilla 的强项：cost-per-success、per-turn tier routing、reasoning policy、tool compression、diagnostics、replay、cache continuity、长会话可用性。
  • Claw-SWE-Bench 的强项：统一 prompt / budget / patch extraction / cost reporting / Pareto frontier / Lite subset selection。它把 harness 也变成了评测对象。
  • 对我们的写法要求：第一段直接写固定任务批次、共享硬预算、任务价值、verified outcome，避免泛化口号。
  • 对我们的真实帮助：它们逼我们把 Main Claim 收缩成更准确的话：固定任务批次下，跨任务地分配共享预算，并按任务价值结算 verified value。
问题 OpenSquilla / Claw-SWE-Bench BudgetFlow
主要关心什么 让 agent 在单次会话或统一评测协议下更强、更省、更可观察 让一批任务在同一个 shared hard budget 下拿到更高的总价值
决策粒度 per-turn、per-session、per-harness cross-task allocation
有没有任务价值 关注 cost-per-success、harness 可比性和 cost-aware evaluation 有，且运行前冻结
有没有共享硬预算 Claw-SWE-Bench 报告 fixed prompt / runtime budget / cost；OpenSquilla 管 per-turn/session cost behavior 有，这是 Claim 1 的核心
我们该吸收什么 更硬的 cost/cache/trace/replay/reporting 习惯 继续把 allocation、coverage、sensitivity 和 frontier gap 讲清楚

主要相关工作怎么摆

工作 它做什么 和 BudgetFlow 的关系 BudgetFlow 的区别 在论文里怎么写
RouteLLM
ICLR 2025; arXiv 2024		 给单个 query 选便宜模型还是贵模型，本质是 per-query router。 很适合启发我们的 RouteLLM-inspired learned router baseline；它的原始问题设置聚焦 per-query cost/quality routing。 BudgetFlow 不只判断“这一条该上哪个模型”，而是判断“整批任务里下一笔 scarce budget 该花给谁”。 直觉例子：用户只发来一条消息：“帮我写一封更正式的邮件。” 系统判断这一次回复值不值得上 GPT-4。
写成“强启发来源”，服务于 learned task-router baseline。
Cascade Routing
ICML 2025 / arXiv 2024		 研究单个 query 上多模型级联怎样在 cost-quality 上最优。 它说明 per-query routing/cascade 这条线已经很成熟；BudgetFlow 把预算竞争提升到跨任务层面。 BudgetFlow 在很多任务之间做预算分配与止损。 直觉例子：像客服分诊。先让便宜模型答一次；如果看起来不靠谱，再升级到更强模型重答。目标是把这一条请求答好。
写成 per-query routing 的强代表工作。
RouteNLP
ACL 2026 Industry Track		 在企业场景里尽量省钱，同时保证质量不低于某个门槛。 它解的是“在质量约束下最小化 cost”，我们解的是“在 cost 约束下最大化 value”。方向相反。 BudgetFlow 接受“预算就是硬上限”这个前提，然后问在这条硬约束下怎么拿到更多 verified value。 直觉例子：像一个客服团队经理说：“今天 5000 条用户消息，怎么把钱尽量省下来，但满意度绝不能跌破红线？” BudgetFlow 的互补视角是：预算固定时先救哪种任务。
非常适合写成“inverse objective”的对照。
BAMAS
AAAI 2026		 在单个 task 内部给多 agent / 多 role 分模型与预算。 它强在 task 内部的 architecture design；我们强在 task 之间的 budget governance。 BAMAS 解决“一个任务内部谁该用强模型”，BudgetFlow 解决“很多任务之间谁更值得先拿预算”。 直觉例子：同一个编程任务里有三个角色：planner、critic、executor。问题是：谁该配强模型，谁用便宜模型就够了？它优化的是一个任务内部的分工。
写成“within-task budgeted system”的最近邻。
INTENT
2026 arXiv preprint		 在单个任务里规划工具调用，让该任务在自己的预算内完成。 它是任务内部规划层；BudgetFlow 是任务之间分配层。两者是上下两层。 INTENT 管“这个任务内部还要不要继续花”，BudgetFlow 管“整批任务里该把钱留给哪个任务”。 直觉例子：像一个 agent 在做法律检索任务。它已经调了几次工具，现在要判断：还要不要再调一次贵 API，还是该停了？它关心的是这个任务内部怎么花。
写成 scope 不同、可互补的工作。
UCCI
2026 arXiv preprint		 把 model uncertainty 校准得更好，让升级/不升级更稳。 更像是可以改进 Model Fit 的部件，适合放在机制层讨论。 UCCI 改善的是“升级判断更准”，BudgetFlow 解决的是“预算治理目标是什么、该先救谁”。 直觉例子：像一个更稳的“升级提示器”。它不替你决定整批预算怎么分，只是帮你更有把握地判断：这一次从小模型升级到大模型，到底值不值。
放到机制层或 Claim 2 讨论里更合适。
vLLM / SGLang / NVIDIA Dynamo
vLLM: SOSP 2023 + prefix caching docs; SGLang: NeurIPS 2024; Dynamo: official docs		 把 LLM inference serving 做成高性能执行层：batching、prefill/decode、KV/prefix cache、priority scheduling、cache-aware routing。 它们是 BudgetFlow future work 的真实 substrate，也说明 agentic inference 是值得研究的系统问题。 BudgetFlow 研究 Task Value、shared budget 和 verified outcome 如何形成 priority、continuation、strong-model opportunity 等信号。 直觉例子：像数据中心已经有一套高速路网；BudgetFlow 研究的是预算有限时，哪些任务的车先上路、哪些继续跑、哪些及时下线。
正文要清楚写出它们和 BudgetFlow 的边界，篇幅保持克制。
Related Work 保持收敛：正文重点写 OpenSquilla / Claw-SWE-Bench、RouteLLM、RouteNLP、BAMAS、INTENT；vLLM / SGLang / Dynamo 要写清楚 serving substrate 与 value-aware batch governance 的边界。 ORBIT、RouteJudge、LLMRouterBench、OpenRouter、Portkey、Langfuse 这些一笔带过即可，主线保持集中。

这会怎样改变我们的论文写法

  • 第一段要更收敛。 直接说：固定任务批次、一个共享硬预算、任务价值不同、结果由 verifier 结算。
  • Claim 1 的主表要同时报标准指标和论文指标。 也就是 Resolved Count / Resolved Rate 加上 Total Resolved Value / TRV per Dollar。
  • 要明确承认 OpenSquilla / Claw-SWE-Bench 的工程强度。 这样不是示弱，而是让我们的边界更可信。
  • 要把 strongest baseline 保持强。 pure T3、RouteLLM-inspired、budget-only 都不能偷着削弱；BudgetFlow 输了就诚实写边界，赢了才更有说服力。
  • Related Work 的落点是：别人解的是相邻问题，我们解的是这个更具体、更窄但也更清晰的问题。

最后一句人话

审稿人版本

  • OpenSquilla / Claw-SWE-Bench 证明了 cost-aware agent runtime 和 cost-aware benchmark 已经很成熟。
  • BudgetFlow 要守住的贡献是：当一批任务共享一个硬预算、任务价值不同、结果可验证时，怎样做跨任务预算治理。
  • 只要这句话立得住，related work 就会增强我们的边界。
