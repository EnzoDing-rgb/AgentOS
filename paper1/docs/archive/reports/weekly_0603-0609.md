****# 周报草稿

过去一周，工作主线很清楚，分成两块：一是机制和策略解耦，二是实验持续推进。前者是在把系统从“能跑”推进到“可解释、可扩展、可对比”；后者是在用更严格的诊断去验证，这套机制到底是在真正提升价值，还是只是在某些任务上看起来有效。

机制层面，我们把 TaskAdapter、ValueSource、ModelCatalog 这些边界重新整理清楚了。TaskAdapter 负责把外部任务接入统一语义，ValueSource 独立提供价值口径，ModelCatalog 则只管模型、价格和能力目录的注册与查询。这样以后，系统可以更容易接入不同企业、不同任务和不同模型目录，不必依赖某一套固定配置，也更方便后续做跨场景比较。

学习与可观测性层面，这一周也完成了关键拆分。Cost Memory、Routing Memory、Escalation Memory 已经从混合逻辑里拆出来，变成可审计、可显式启用的机制；Memory 不会默认偷读历史数据，必须在当前运行里明确打开，才能进入决策链路。这个变化的意义不只是工程清爽，而是让我们能区分“系统真的学到了什么”与“只是借用了过去的痕迹”。

实验上，3x8 diagnostic 在 learning off 条件下给出了不错的正向信号。BudgetFlow same-router 达到 6/8，bare strong 是 4/8，enterprise router 是 2/8；更重要的是，三种价值口径下结论同向，说明当前信号不是单点偶然，而是有一定一致性。这个结果说明机制方向基本站得住，但还不足以代表最终形态。

更有价值的是 4x12 实验。它没有被简单理解成失败，而是暴露出一个更关键的问题：当强模型的价格和能力结构发生变化时，系统目前对新的模型 tier frontier 学得还不够快，routing 还不能很好适应新的成本结构。我们是通过改变模型成本和强模型基线来测试机制在不同价格结构下的鲁棒性，这一步帮助我们更准确地定位下一轮机制智能化该往哪里做。后续重点会放在 tier utility calibration 上，并扩大实验规模，继续验证 routing、升级和价值分配是否能在更复杂的价格结构下保持稳定。
