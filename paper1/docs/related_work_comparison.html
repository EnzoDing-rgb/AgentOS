BudgetFlow — Related Work 与本周进展

本文不是省 token、不是级联路由、不是 harness 工程。本文研究：一批任务共享硬预算时，预算如何按预注册价值、任务 effort、模型价格和适配性流动。

Claim 1 & Claim 2

Claim 1 Value-Aware Budget Allocation

机制层：共享账本（Reserve/Settle/Release）、预注册 ValueSource、stop-loss 原语、JSONL 审计追踪——Claim 1 和 Claim 2 的共同基础设施。
Budget Regime Compiler：任务集 + ValueSource + Task Effort + catalog + Cost Memory + target pressure → 共享 hard cap。编译后冻结。
运行时分配：在编译的硬预算下，按 Task Value / Effort / Model Fit / 预算压力分配 spend，最大化 Yield 和 Yield per Dollar。

Claim 2 路由策略

在机制层之上，value-aware 路由策略——Tier Boundary Selection、task-level 选型、segment 切换、止盈止损、memory——在诊断控制下改进或保持 Yield/Dollar。

本文的价值与泛化性

不是为了打赢 SWE-bench 随手调参。真实企业上线前本来就必须校准预算、任务价值、模型价格和模型适配性；本文的贡献是把这件事做成可预注册、可审计、少参数、跨任务泛化的机制。

1. 泛化性不在参数，在抽象。泛化性不体现在"某个 SWE-bench 参数调对了"，而体现在预算、任务价值、模型价格、模型适配性都被抽象成可预注册、可审计、可替换的输入。

2. Compiler 替代拍脑袋。Budget Compiler 由任务集、Value Matrix、模型目录和校准证据共同生成硬预算，决定这批任务到底应该有多紧，而不是事后手工改 cap。

3. 调参合理，但只调抽象规则。真实企业部署前也必须校准——调的是 target utilization、价格 catalog、价值来源、模型适配先验，不能针对某个 benchmark task 开后门。

4. 可迁移性。同一套预注册→编译→运行→审计流程可迁移到别的任务域，只需替换 value source、model catalog 和历史校准证据。

为什么上周能赢、这周反而难赢

1. 上周赢的不是当前 task-level。上周赢的是更接近 budgetflow_full / segment-aware 的完整机制：任务内换挡、T3 rescue、Value-Triggered Escalation、stop-loss、共享预算。这个机制更强也调得更久，赢 bare T3 / enterprise 是正信号，但不能直接证明 task-level 一次选型已经能赢。
2. 这周发现的 bug/设计混淆污染了上周结论。budget_pressure 曾混合"预算松紧"和"卡住要升级"两个反向信号，T3 使用可能带偶然性。task-level 曾和 segment 路径搅在一起，不能回答"谁在开 T3"。Budget Compiler 曾把 cap 压得过紧，很多 run 测的是预算饿死不是策略。
3. 上周结果最合理的解释：有真实正信号，但口径不干净。BudgetFlow full 可能确实靠 value-aware routing 和适度强模型使用提升了 yield，但旧实验混有任务集偏熟、14 strategy/dedup 噪音、分类/abort 口径、旧价格比例、旧 cap 等问题。它可以作为方向性证据，不能作为最终 Claim 1 证据。
4. 这周难赢的根因不是机制没价值，是证据标准提高了。六策略同入口、compiler 生成预算、task-level 一次选型锁定、T3 价格 1:3:15、infra gate 更严格。旧"容易赢"的路径被清理后，真正暴露的是 task-level 初始选型和 submit/stop-loss 质量还不够强。
5. 新 6×5 早期信号：Compiler 过紧已缓解。bare T3 能连续跑多个任务，task-level 首任务 T2 46 turns pass。新重点不是预算饿死，而是 task-level 单任务耗时/耗钱偏重，以及 gold edit 后 submit/stop-loss 是否浪费预算。

如何读 6×5：bare baseline 与 Claim 1 的关系

论文主张不是"每轮都必须同时打赢 all-T2 和 all-T3"。核心是：同一共享硬预算下，按任务价值和成本压力分配预算，最大化 verified Yield。all-T2 / all-T3 是诊断镜子，不是唯一胜负线。

all-T3 是能力上界，但不一定预算可持续。尤其在 minimal cap 下可能提前耗尽，pass 高但 Yield per Dollar 低。

all-T2 是省钱下界，但会牺牲高价值 / 困难任务。便宜但可能漏掉该用强模型才能解的任务。

BudgetFlow 在两界之间做价值导向分配。如果 T3 pass 多，看是否成本高、是否把钱花在低价值任务上；如果 T2 便宜，看是否漏掉高价值任务。Claim 1 证据是固定预算下的 normalized verified Yield，不是 pass count。
