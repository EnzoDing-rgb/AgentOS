# AgentOS: A User-Space Resource Kernel for Concurrent LLM Agents

## 这篇论文到底要干什么（一句话 + 三个问题 + 一个方案）

**一句话目标：** 在多 agent 并发调用 LLM 的真实系统里，把“花钱的 token、会限流的 API、有限的并发请求槽”当作一等资源来管理，让系统在**预算约束**下依然能提供可预期的延迟/吞吐/公平性（QoS），并能自动止损跑飞任务。

**要解决的是什么问题：**

- **预算不可再生**：token 直接等价于美元，花完就没了；现有编排框架通常不做全局预算规划，导致低价值任务提前烧光预算，高优任务后续无法执行。
- **共享限流与并发互相踩踏**：多个 agent 共用同一 API key 的 RPM/TPM 与并发上限，缺少协调会产生大量限流错误/排队抖动；长跑后台任务容易把交互式任务卡死。
- **“活着但没进展”的 zombie**：LLM/工具调用可能进入语义 livelock 或超时卡死，占着并发槽与预算预留，用户只能手动 kill / new context。

**解决方案是什么（AgentOS 的核心设计）：** 在用户态实现一个“LLM 资源内核”，把治理与调度解耦为两层，并通过统一入口把所有 LLM 调用纳管。

- **Resource Governor（治理层，工程保底）**：做预算时间分布（Budget Governor）、全局限流协调（Rate Limiter）、以及 Turn 级准入控制（Admission Control），避免 overcommit，并给出可验证的资源红线。
- **Multi-Backend Scheduler（调度层，研究增益）**：在 Governor 红线内做异构后端的模型选择（cost-quality tradeoff）、优先级队列与（可选）抢占、以及 zombie 检测与回收，提高交互任务的响应并降低无效消耗。
- **Unified LLM API Gateway（统一入口）**：上层 agent 只调用 `llm.call()`；Gateway 负责拦截→调度决策→执行→计量回收，实现“对上层透明、对资源可控”。

**关键研究点（这篇论文想证明/证伪什么）：**

- **多后端 + 全局预算约束的在线调度**：不是单请求路由，而是在多任务、长时间、并发竞争下做跨时间的 cost-quality 决策（带预算水位信号）。
- **抢占是否可行**：提出并实证评估一个实验性机制 **语义存档（archive/resume）** 来支持粗粒度抢占；它是有损且有成本的，论文要量化它的成功率/开销/适用边界。
- **自动止损与恢复**：用 zombie 检测把“用户手动 new context/kill”变成系统自动回收协议，释放并发槽与预算预留。

## 核心 Insight

现有 agent 编排框架把 LLM 资源当作“免费但稀缺”的传统资源来管理（排队、限流、配额），但 LLM 的 token 是**带价格标签的可耗竭资源**：每次调用直接花钱，预算用完就无法“补回”。更重要的是，不同模型后端（GPT-4o、Claude Sonnet、本地 7B）在成本/质量上差异极大，同一个任务路由到不同后端，花费可相差 10–100 倍。因此调度器必须在**预算约束下**跨后端做实时的 **cost-quality tradeoff**，而不仅是排队。

多 agent 并发下有两类互补问题：**资源治理**（上限、准入、限流、预算）与**任务调度**（争抢时谁先用、谁让路）。现有框架通常只做编排。我们在用户态实现一个“LLM 资源内核”：**Resource Governor** 负责预算规划/限流/准入；**Multi-Backend Scheduler** 负责模型选择、优先级、抢占与僵尸回收。抢占依赖一个实验性机制——**语义存档（archive/resume）**——用实证研究回答“有损抢占是否可行、代价多大、边界在哪”。

语义存档在这里不只是「让路」。在按 token 计费的前提下，把整段轨迹原样堆进 context 往往既不划算，也容易让关键信号淹没在噪声里；把现场压成「摘要 + 续跑指令」，是在预算与抢占约束下**主动收缩有效上下文**。这与「用检查点保留结论、而非全量重放轨迹」是同一类思路，区别只在触发条件是抢占还是失败续跑——后者在工作流恢复的设定里另有展开。另一类常见负载来自 ReAct 式行为：推理铺得很长、工具却迟迟不落地的回合，在系统侧与语义 livelock 一样——仍在消耗 token 与并发槽，却没有可观测进展。AgentOS 在 **Turn 级**用 Zombie、Progress Oracle 与预算异常做止损；步级「何时多想、何时直接行动」交给策略层，与 Governor/Scheduler 正交，范围界定见后文「不在本文范围内」。

## 一个关键澄清：抢占不是“抢别人上下文”，而是暂停别人占着的共享资源

“每个 agent 都有自己的上下文窗口吗？”逻辑上是对的：对话历史、状态、计划各自独立；但物理上会互相踩踏的是**共享资源**：同一 API key 的 rate limit、全局 token 预算、并发槽（in-flight 请求数）、以及某些工具的排他锁。若只有排队，交互式 Turn 很容易被长跑后台 Turn 卡住；抢占的目标是释放这些共享资源，把“用户在等”提升为系统级优先级。

## 术语与缩写

| 缩写 / 术语 | 全称或含义 | 在 AgentOS 里指什么 |
|---|---|---|
| **Turn** | 一轮完整的 agent 交互 | 调度与计量的基本单位：一次模型推理 + 可能多步 tool call。 |
| **语义存档** | archive / resume | 把当前对话/任务进展压成「摘要 + 续跑指令」存到存档库；需要时用它重建上下文继续跑。**有损**，恢复后状态≠原始状态。 |

| **TTFT** | Time To First Token | 从发起请求到模型输出第一个 token 的延迟。 |
| **QoS** | Quality of Service | 对延迟、吞吐、公平性给出可预期的保证。 |
| **overcommit** | 过度承诺 | 接纳任务的资源需求总和超出系统上限，导致大面积失败。 |

## 问题定位

LangChain、CrewAI、AutoGen 等解决了 agent **编排**，但缺少系统性的**资源治理与调度**，典型表现为：

**约束缺失（没人管上限）：** 10 个并发 agent 共享同一个 API key，没有任何 token budget 分配和 rate limit 协调机制。一个跑飞的 agent 可以把 token 预算耗尽，其余 agent 只能饿死。系统因并发请求过多直接打到 API 限流错误，崩掉整条流水线。

**调度缺失（没人管顺序）：** 高优先级任务（用户实时交互）和低优先级任务（后台批处理）争抢同一个上下文窗口，互相阻塞，没有优先级机制。僵尸 Turn——卡死、超时、语义上原地打转——继续占着 context 槽位和并发槽，用户只能手动 kill 重开。这正是 Cursor 用户频繁遭遇「agent 不动了、只能 new context」的根本原因。

**成本盲目（没人管花多少钱）：** 所有请求无差别地发往同一个昂贵模型，不区分任务难度。一个简单的格式转换和一个复杂的架构设计用同一个 GPT-4o，前者浪费了 90% 以上的成本。没有全局预算意识——前半天把钱花光，后半天高优先级任务无法执行。没有跨模型的 cost-quality 优化——明明本地 7B 就能做好的任务也在烧云端 API 额度。

三者彼此放大：无约束→滥用；无调度→滥用者不可打断；无成本意识→预算被低价值任务提前耗尽。

## 核心抽象：三类 LLM 一等资源

AgentOS 将 LLM 相关资源抽象为三类一等公民，每类有不同的管理语义：

**Token 预算（可耗竭、带价格）。** 与传统 OS 管理的 CPU 时间（可再生、免费）根本不同：token 用完不可恢复，且每个 token 有明确的美元价格。更复杂的是，同一个 token 在不同后端的价格不同（GPT-4o 输出 token 的价格是 GPT-4o-mini 的 ~25 倍）。预算管理必须同时考虑**总量约束**（日/周美元上限）和**时间分布**（避免前半段耗尽导致后半段饿死）。

**API 速率（可再生、有弹性）。** 类似传统 OS 的 I/O 带宽：有短期突发上限（RPM/TPM），但窗口滑动后恢复。不同后端的速率限制独立，可以并行利用。

**并发槽位（排他、有限）。** 类似传统 OS 的进程槽或文件描述符：同时在飞的请求数有硬上限，需要排他分配。

关键观察：传统 OS 调度器主要优化 CPU 时间分配（一维、免费、可再生）；LLM 调度必须在以上三维联合决策，其中最关键的 token 预算是**带价格且不可再生**的。不同后端在价格/速率/并发特性上都不同，调度器需要结合任务需求与剩余预算做联合选择。

## 架构概览：Resource Governor + Multi-Backend Scheduler

```
┌──────────────────────────────────────────────────────────┐
│            Agent 应用层 (LangChain / CrewAI / etc.)       │
├──────────────────────────────────────────────────────────┤
│                  Unified LLM API Gateway                   │
│   llm.call(prompt, task_type, priority) → result          │
│   （对上层透明：agent 不知道底层用了哪个模型）              │
├──────────────────────────────────────────────────────────┤
│                                                            │
│   ┌─ Resource Governor (Governance) ──────────────────┐  │
│   │  Budget Governor     — 预算规划与时间分布管理       │  │
│   │  Rate Limiter        — API 调用速率协调             │  │
│   │  Admission Control   — Turn 准入检查                │  │
│   │  (独立运作，不依赖语义存档)                           │  │
│   └────────────────────────────────────────────────────┘  │
│                                                            │
│   ┌─ Multi-Backend Scheduler ─────────────────────────┐  │
│   │  Model Selector      — 任务-模型匹配，cost-quality  │  │
│   │  Priority Scheduler  — 多级队列，Turn 级调度        │  │
│   │  Archive Engine      — 语义存档/续跑生成与恢复       │  │
│   │  Zombie Detector     — 僵尸 Turn 检测与回收         │  │
│   └────────────────────────────────────────────────────┘  │
│                                                            │
│   ┌─ 基础设施 ─────────────────────────────────────────┐  │
│   │  Archive Store       — 语义存档持久化               │  │
│   │  Auto-Prober         — 后端能力-成本画像自动探测    │  │
│   │  LLM Driver Pool     — 异构后端统一驱动             │  │
│   │    (OpenAI / Anthropic / Local vLLM / Ollama)       │  │
│   └────────────────────────────────────────────────────┘  │
│                                                            │
└──────────────────────────────────────────────────────────┘
```

**关键设计决策：治理与调度分离。** Resource Governor（Budget / Rate Limiter / Admission Control）不依赖语义存档，用 FIFO + 计数器即可工作；即使语义存档被证明不可行，Governor 仍然独立提供确定性价值。Multi-Backend Scheduler 在 Governor 的预算红线之内添加模型选择、优先级与抢占能力，语义存档是 Scheduler 的实验性机制。

**统一 API Gateway。** 所有 agent 的 LLM 调用经过 Gateway：拦截请求→向 Scheduler 取调度决策（后端选择、token 配额、是否排队）→转发执行→回收实际消耗与质量反馈。对上层透明：agent 只调用 `llm.call()`，无需关心底层模型。

## Resource Governor：预算规划与准入控制

Governor 是系统的工程底座，重点是可预期与可验证。

**Auto-Prober（后端自动探测）**：系统启动时自动向每个配置的 LLM 后端发送探测请求，构建一张**能力-成本画像表**：上下文窗口大小、每 token 价格（输入/输出分开计）、实测延迟中位数、实测速率上限。用户只需填 API key，不需要手动填任何参数。运行中持续校准（延迟和可用性会变）。画像表是 Scheduler 做模型选择的基础数据。

**Budget Governor（预算治理器）**：维护“期望消耗曲线 vs 实际消耗曲线”。用户给出日/周预算上限与应急储备，Governor 生成期望曲线并在线校正：消耗偏快则收紧（更便宜模型/推迟低优任务），消耗偏慢则放宽（允许更多高质量模型）。这是一种在线预算规划，而非每次请求的二元闸门。

**Rate Limiter**：启动时通过 Auto-Prober 读取 API 响应头（`X-RateLimit-*`）自动获取限速参数，无需手动配置。多 agent 共享一个滑动窗口计数器，按优先级分配调用额度。多个异构后端的速率限制独立管理，可并行利用。

**Admission Control**：Turn 进入调度队列前必须通过三项检查——token 预算余额是否够本次 Turn 的估算消耗、rate limit 余量是否能在合理时间内完成、并发槽是否有空位。不满足则排队等待或拒绝。这避免了"承诺了资源却跑不起来"的 overcommit。

即便没有语义存档、也没有复杂调度，单靠预算规划 + 限流 + 准入控制，通常就能显著优于“裸跑”。

## Multi-Backend Scheduler：多后端调度与语义存档

Scheduler 是研究部分：在 Governor 红线内做多后端选择、优先级与（可选的）抢占。

### 异构模型选择

每个 LLM 调用到达时，Scheduler 做联合决策：选择后端、分配 token 配额、决定立即派发或排队（时机）。

可视为一个在线优化：在剩余预算约束下最大化加权质量。给定剩余预算 \(B_{\text{remain}}\)、任务权重 \(w_t\)、后端 \(m\) 的预估质量 \(q(t,m)\) 与成本 \(c(t,m)\)，对每个请求做：

```
argmax_{m ∈ M}  w_t · q(t,m) / c(t,m)

s.t.  c(t,m) ≤ B_remain - B_reserve,  rate(m) < limit(m)
```

其中 q(t,m) 是从历史执行记录中学到的——同类型任务在不同模型上的输出质量（用 LLM-as-judge 或任务特定指标自动评估），跑几次就能建起来一个 **quality profile**。

**与单请求路由的本质区别：** RouteLLM、FrugalGPT 等工作优化的是单个 query 的 cost-quality tradeoff，没有 budget 概念，也不考虑并发和时间维度。我们做的是多 agent 并发流水线下的、有全局预算约束的、跨时间的在线调度。这是一个 **online knapsack / online packing** 变体，有理论深度可做 competitive ratio 分析。

### Priority Scheduler

维护多级优先级队列，调度单位是 Turn。高优先级 Turn（用户交互）可以抢占低优先级 Turn（后台批处理），抢占触发语义存档机制保存被抢占者的状态。

### 语义存档：有损的“保存现场 / 续跑”

**这是本工作的核心研究假设，不是已验证的成熟原语。**

LLM 的“对话状态”是语义信息，不能直接做无损快照。语义存档的做法是：

```
抢占时：Summarizer(当前 context) → 压缩摘要 + 续跑指令 → 存入 Archive Store
恢复时：从 Archive Store 取出 → 重建 context → 继续执行
```

**语义存档的关键代价必须正视：**

**有损性。** 语义存档是有损压缩——续跑后的状态在语义上不等于原始状态。可用性取决于经验测量：在目标任务上，续跑后的 agent 能否以可接受的成功率继续完成工作？

**自身代价。** 生成语义存档需要调用 LLM 做摘要，这消耗的正是系统试图管理的稀缺资源（token 和 rate limit）。存在一个临界点：当抢占频率超过某个阈值，存档/续跑的开销会吃掉它带来的调度收益。这个临界点是多少，需要实验测量。

**延迟。** 语义存档是秒级（一次完整 LLM 推理）。这意味着它不适合高频切换，只适合粗粒度、低频的抢占场景——例如一个长跑的后台任务被实时交互打断。

**语义存档的研究假设：** 在低频抢占（分钟级，非秒级）、任务可容忍一定信息损失的场景下，语义存档的收益（高优先级任务延迟降低）能够覆盖其代价（token 消耗 + 续跑成功率损失）。如果实验否定了这个假设，Scheduler 的贡献退化为"仅队列优先级 + zombie 回收"，Governor 的贡献不受影响。

### Zombie Detector

这是 Scheduler 中最“工程可落地”的部分：对活跃 Turn 做活性监控与止损。

**心跳超时。** T 秒内无 token 输出、无 tool 返回 → 捕捉 API 沉默和工具阻塞。这是最简单的检测层，覆盖硬性卡死。

**进展预言机（Progress Oracle）。** 追踪 Turn 的状态指纹——tool 调用序列、输出内容 hash、关键变量变化。连续 N 步无新状态 → 判定语义 livelock。这一层针对的是 LLM zombie 的独特形态：模型在语义上原地打转（反复调用同一工具、输出重复内容），但从 API 层面看起来"还活着"。若 ReAct 式回合长时间停留在推理而**无新 tool 效果、无状态推进**，也按同一标准视为无进展。

**烧钱速率异常。** Token 消耗速率偏离同类任务基线（例如一个通常 2000 token 完成的任务已经烧了 15000 且仍未结束）→ 提前止损，与 Budget Allocator 联动。

**回收协议：** 判定 zombie → 生成语义存档保留已完成中间结果（若语义存档不可用则直接丢弃并记录日志）→ 释放 context 槽位、并发槽、预算预留 → 将任务标记为可重试。这把用户手动「new context window」变成系统自动行为。

## Governor 与 Scheduler 的协作：一个 Turn 的生命周期

两者在 Turn 生命周期中形成闭环：

- **Governor 管总量与资格**（预算规划、准入、限流红线）
- **Scheduler 管分配与让路**（模型选择、排序、抢占、回收）
- **Governor 的预算水位信号影响 Scheduler 的模型选择策略**（预算紧张时倾向便宜模型），Scheduler 的回收/抢占/完成会反过来更新 Governor 的账本

一个 Turn 从提交到结束的端到端流程如下：

1. **Turn 提交**
   - `submit_task(priority, resource_spec)` → 生成 Turn，并携带优先级与资源需求估算（预算/并发/速率）

2. **Admission Control（Governor，入口门卫）**
   - 检查 **budget 余额/预留**、**rate limit 窗口余量**、**并发槽** 是否满足
   - 不满足：排队等待或拒绝（此时 Scheduler 不会看到这个 Turn）
   - 满足：进入 **Priority Queue（Scheduler）**

3. **Scheduling（Scheduler，模型选择 + 队列派发）**
   - 根据优先级 + 任务类型 + 当前预算水位（来自 Governor）选择下一个 Turn 派发，并决定发往哪个模型后端
   - **预算水位驱动模型选择**：预算充裕时高优任务用最强模型；预算紧张时自动降级到更便宜的后端、或更积极回收低优先级 Turn

4. **Dispatch & Runtime Metering（Governor，运行时计量与限流）**
   - 派发时执行 rate limit 的最终检查（避免队列等待期间窗口变化导致超限）
   - 执行中持续计量 token 消耗，更新预算账本与滑动窗口

5. **Liveness Monitoring（Scheduler，Zombie Detector）**
   - 运行中持续监控：心跳超时 / 进展预言机 / 烧钱速率异常
   - 若判定 zombie：回收并释放资源（并通知 Governor 结算与归还）

6. **Preemption（Scheduler → Governor，抢占与归还）**
   - 当高优先级 Turn 到达且并发槽已满时：
     - Scheduler 选择低优先级 Turn → `archive()`（若启用语义存档）
     - 释放并发槽与（可释放的）预算预留，**将资源归还给 Governor**

7. **Completion（Governor 结算，Scheduler 出队）**
   - 正常完成：Governor 结算实际消耗、释放预留与占用；Scheduler 将 Turn 标记完成并出队

## 执行模型的诚实限制

**AgentOS 是用户态软件，没有硬件级 enforcement boundary。** 任何框架都可能绕过 AgentOS 直连 LLM API。AgentOS 提供的是**协议级**隔离与 QoS：只有参与者通过 AgentOS API 交互时才获得保证，不应将其表述为内核级强制隔离。

**AutoProbe 的 rate limit 探测依赖 API 厂商在响应头中暴露信息。** 如果厂商不暴露或信息不准确，需要退回手动配置或启发式估算。

## 不在本文范围内的问题

**工具安全 / 语义防火墙。** Agent 工具调用的安全审查（意图级门控、效应分析、原子回滚）是一个重要但正交的问题。它不依赖资源调度，也不被资源调度所依赖。我们将其作为独立的未来工作。

**步级元策略（何时深度推理、何时直接行动）。** 本文只做 Turn 级准入、调度与止损；由策略层或上层 agent 决定「少 Think 多 Act」不在本文范围，与 Paper 2 的作用域恢复、Paper 3 的动作门控可组合。

**服务端推理调度。** vLLM 等系统在服务端做 KV cache 管理和请求调度。AgentOS 工作在客户端/编排层，与服务端调度互补但不重叠。

## 与相关工作的对比

| 系统 | 解决什么 | 没解决什么 |
|---|---|---|
| Sovereign-OS | 财务治理、权限、审计 | 并发资源调度、异构模型选择、context preemption |
| RouteLLM / FrugalGPT | 单请求维度的 cost-quality 路由 | 全局预算约束、时间规划、并发调度 |
| AgentRM | Zombie Turn 检测、Turn 级资源计量 | 主动抢占、跨 agent 全局调度、异构后端 |
| vLLM | 服务端 KV cache 调度 | 客户端多 agent 资源治理 |
| **AgentOS** | 预算感知异构调度（模型选择 + temporal planning）+ 资源约束（配额 + 准入）+ 调度（优先级 + zombie 回收）+ 语义存档抢占（实验性） | 语义存档有损性的理论界限、强制隔离、工具安全 |

## 研究问题与实验计划

### RQ1：Governor 的基线价值（工程验证）

在 10-50 个并发 agent 共享一个 API key 的场景下，仅靠 Budget Governor + Rate Limiter + Admission Control（无抢占、纯 FIFO、固定模型），相比无治理的裸跑基线，任务完成率和 API 错误率改善多少？

预期：这是工程工作，改善幅度应当显著且可复现。目的是建立"即使没有异构调度和语义存档，Governor 本身已有价值"的 baseline。

### RQ2：多后端调度的 cost-quality 收益（核心研究问题）

三组对比：

**Baseline A — 固定模型 + 无预算管理（现状）。** 所有请求发给同一个模型（如 GPT-4o），花完拉倒。展示系统在相同预算下完成更多任务，或同等任务量花更少钱。

**Baseline B — 有优先级队列和速率限制，但所有请求用同一个模型，budget 只做硬截断。** 即 Governor + 单模型。展示异构模型选择 + temporal planning 带来的增益。

**Baseline C — RouteLLM / FrugalGPT 式单请求路由。** 每个请求独立优化 cost-quality，但没有全局预算意识和时间规划。展示 temporal planning 在长时间多任务场景下的优势——它们会在前半段把预算花光，导致后半段无法执行高优任务。

关键指标：总花费、任务完成率、平均输出质量、预算利用率（花了多少占 budget 比例）、**质量方差**（是否所有任务都稳定，而不是前面质量高后面质量崩）。

### RQ3：语义存档的可行性边界

在不同任务类型（代码生成、信息检索、多轮推理）和不同 context 长度下：（a）续跑后的任务继续完成的成功率是多少？（b）生成与续跑的 token 开销占原始任务 token 的比例是多少？（c）存在何种条件下语义存档的代价超过其收益？

这是本文的核心实验之一。如果成功率过低或开销过高，结论是"LLM 场景下的抢占式调度在当前技术条件下不可行"——这本身也是有价值的负面结果。

### RQ4：语义存档抢占对高优先级任务的延迟改善（条件性验证）

如果 RQ3 证明语义存档在某些任务类型上可行，那么在混合负载（高优先级交互 + 低优先级批处理）下，语义存档抢占相比纯排队等待，高优先级任务的 TTFT 降低多少？

### RQ5：自动 Zombie 回收的效果

自动 Zombie 检测 + 回收 vs. 人工 kill + 重启，在并发场景下的资源利用率和端到端任务完成时间对比。Zombie Detector 的三层检测中，哪一层贡献了最多的有效检出？

## 为什么值得做

**问题真实且有经济意义。** 多 agent 并发场景下的预算浪费是真金白银的损失。一个团队每天跑几十个 agent，如果所有请求无差别地打到最贵的模型，成本可以轻松降低 50-80%。这不是理论问题，是每个使用 LLM API 的团队都面临的实际痛点。

**问题定义清晰，有理论深度。** Budget-constrained online scheduling over heterogeneous backends 是一个 well-defined 的 online optimization 问题（online knapsack / online packing 变体），可以做 competitive ratio 分析，有理论贡献空间。

**Governor + 异构调度保底。** 即使语义存档失败，预算规划 + 异构模型选择 + 准入 + zombie 回收已经构成一个有用的系统贡献。论文不会因为一个假设被否定而全盘作废。

**语义存档无论成败都有研究价值。** 如果可行，它是 LLM 系统的新调度机制。如果不可行，我们给出的量化分析（在什么条件下、因为什么原因不可行）同样填补了这个领域的认知空白。

**Scope 可控。** 纯用户态，不碰 LLM 服务端，一个人可以做出原型。
