# 大模型推理第一性知识

本文档解释大模型推理过程中的显存占用和性能基本原理，所有概念都用直白语言说明。

---

## 术语解释

| 术语 | 直白解释 |
|------|----------|
| 参数（权重） | 神经网络训练学到的数值，模型能"说话"全靠这些参数。参数越多，模型能力越强，但占用显存越大。 |
| B | 十亿，27B 就是 270 亿参数，35B 就是 350 亿参数，激活 3B 就是推理时只用 30 亿参数计算。 |
| Token | 模型处理文本的基本单位，中文 1 个 token 约等于 1-2 个汉字，英文 1 个 token 约等于 0.7 个单词。 |
| FP8 / BF16 / INT4 | 数值精度，精度越低每个参数占用字节越少，显存占用越小，但模型输出质量可能有损失。 |
| 上下文长度 | 模型能一次性处理的总 token 数，包括你的问题和模型之前生成的回答。越长能处理的对话/代码越多。 |
| 并发 | 同一时间处理多个用户请求。 |

---

## 1. 显存到底被什么占了

一张 80GB 显存的显卡，加载大模型后，显存被三部分占用：

| 名称 | 作用 | 大小（27B-FP8） | 是否固定 |
|------|------|-----------------|----------|
| 模型权重 | 存储神经网络的参数，模型加载后就不变 | ~27GB | 固定 |
| KV Cache | 存储已经生成过的 token 的键和值，避免重复计算。越长的对话占用越多 | 动态变化 | 可变 |
| 运行时开销 | 其他临时数据，比如处理图像的编码器 | ~5GB | 固定 |

**核心公式：**
```
总显存占用 ≈ 权重 + KV Cache + 运行时开销
```

**关键点：**
- 权重是固定成本，一旦加载就不变
- KV Cache 是可变成本，上下文越长、同时处理的请求越多，占用越大
- 80GB 显卡跑 27B FP8，权重加运行开销约占 32GB，还剩 ~48GB 可以给 KV Cache

## 2. Dense 和 MoE 两种架构的区别

### Dense（稠密模型，代表：Qwen3.6-27B）

- **结构：** 一整个完整的神经网络，所有参数连在一起
- **每次推理：** 全部 270 亿参数都参与计算
- **特点：** 单次推理速度慢，但所有参数协同工作，逻辑推理连贯性好

### MoE（混合专家模型，代表：Qwen3.6-35B-A3B）

- **结构：** 1 个共享神经网络 + 256 个小的子神经网络（称为"专家"），再加一个路由网络（Router）
- **每次推理：** 路由网络只选择 8-9 个专家参与计算，总激活参数约 30 亿
- **特点：** 单次推理速度快，因为计算量小，但每次只用到部分参数

### 常见误区

**误区：总参数越多模型越聪明。**

**事实：** 推理时的能力取决于**实际激活的参数数量**，不是总参数。35B MoE 总参数 350 亿，但每次只激活 30 亿，推理能力上限由这 30 亿决定。

### MoE 的优势和局限

**35B 总参数的意义：**
- 256 个专家可以分别存储不同领域的知识，模型覆盖的知识面更广，能处理更多种任务
- 每次只激活少数专家，计算量小，速度快，节省算力

**局限：**
- 路由网络根据训练数据学到的模式选择专家。遇到跨多个领域的复杂问题（比如一个 bug 同时涉及操作系统内核、编译器、网络协议），路由网络可能选错专家，或者多个专家的输出无法整合，缺乏全局一致性。

### 实测对比

这就是为什么在代码相关测试中，27B Dense 胜过 35B MoE：

| 测试 | 27B Dense | 35B-A3B MoE |
|------|-----------|-------------|
| SWE-bench（修复代码 bug） | 77.2 | 73.4 |
| Terminal-Bench（命令行任务） | 59.3 | 51.5 |
| SkillsBench | 48.2 | 28.7 |

**原因：**
- 修复真实代码需要对整个系统有全局理解和深度推理
- Dense 全部参数一起计算，逻辑链条能保持连续深入
- MoE 只调用部分专家，跨文件、跨模块追踪 bug 容易出错

### Dense vs MoE 对比表

| 对比项 | Dense（稠密，如 27B） | MoE（混合专家，如 35B-A3B） |
|--------|-----------------------|------------------------------|
| 参数结构 | 一个统一神经网络 | 1 个共享网络 + 256 个专家网络 |
| 每次推理激活参数 | 全部 27B | ~3B |
| 显存占用（FP8） | ~27GB | ~35GB |
| 每 Token 计算量 | 大（27B 次运算） | 小（3B 次运算） |
| 单次推理速度 | 慢 | 快 |
| 适合任务 | 需要深度推理的任务（代码、数学） | 知识检索、简单问答 |

## 3. KV Cache 计算方法

### Qwen3.6-27B 参数

```
层数 = 64 层
KV 注意力头数 = 4 个
每个头维度 = 256
```

### 计算公式

**单层单 Token：**
```
每层每 Token = KV头数 × 头维度 × 2 (K 和 V 各需要存储一份) × 精度字节数(FP8=1)
             = 4 × 256 × 2 × 1 = 2048 字节 ≈ 2 KB
```

**一个请求完整 KV Cache：**
```
KV Cache 大小 = 单层单 Token × 层数 × 上下文长度
             = 2 KB × 64 × 131072
             = 16.7 GB（128K 上下文时）
```

### 不同配置下的 KV Cache 需求

| 上下文长度 | 1 个请求 | 2 并发 | 3 并发 | 4 并发 |
|-----------|---------|-------|-------|-------|
| 32K | 4.2 GB | 8.4 GB | 12.6 GB | 16.8 GB |
| 64K | 8.4 GB | 16.8 GB | 25.2 GB | 33.6 GB |
| 128K | 16.7 GB | 33.4 GB | 50.1 GB | 66.8 GB |

## 4. 推理分为两个阶段，瓶颈不同

| 阶段 | 做什么 | 瓶颈 |
|------|--------|------|
| Prefill（预处理） | 把你输入的全部 prompt 一次性处理完 | GPU 算力（FLOPS） |
| Decode（生成） | 一个一个 token 输出答案 | 显存带宽（GB/s） |

**直白解释：**
- **Prefill：** 输入 1000 字代码，GPU 可以并行计算所有 token，处理速度看 GPU 算力。模型越小，Prefill 越快。MoE 在这里优势不大。
- **Decode：** 模型逐个输出 token，每输出一个都要从显存读取权重。MoE 只需要读 3B 权重，读得快，所以这里 MoE 速度更快。

## 5. 量化：用精度换显存空间

量化是降低每个参数存储精度来减少显存占用。精度越低，显存越小，模型输出质量可能下降。

| 精度 | 每个参数占字节 | 27B 权重大小 | 35B 权重大小 | 质量损失 |
|------|--------------|-------------|-------------|---------|
| FP16/BF16 | 2 | 54 GB | 70 GB | 0%（原始精度） |
| FP8 | 1 | 27 GB | 35 GB | <1%（几乎无损） |
| INT8 | 1 | 27 GB | 35 GB | 1-3% |
| INT4/GPTQ | 0.5 | 13.5 GB | 17.5 GB | 3-10% |

**FP8 的优势：**
- A800/H100 显卡硬件原生支持 FP8 计算，不需要软件模拟，速度不下降
- 采用分块校准量化（每 128 个参数一组校准），不是粗暴砍掉精度，质量损失极小
- 官方测试和第三方测试都证实，性能接近 BF16

## 6. 并发处理原理

vLLM 的 `max-num-seqs` 参数不是让 GPU 同时计算多个请求，而是把多个请求的 KV Cache 预先存在显存里，GPU 轮流处理每个请求的下一个 token。

**核心公式：**
```
总显存 ≈ 权重 + 所有请求 KV Cache 之和 + 碎片/缓存
并发上限 = (总显存 - 权重 - 运行开销) ÷ 单个请求 KV Cache 大小
```

**以 80GB A800 为例：**
- 27B Dense：权重约 32GB，剩余约 48GB 给 KV → 支持 4-6 个长上下文请求
- 35B MoE：权重约 38GB，剩余约 42GB 给 KV → 支持 3-5 个长上下文请求

**结论：** 35B MoE 虽然单次推理更快，但权重占用更多显存，能同时处理的请求反而更少。

## 7. Thinking 模式的显存问题

Qwen3.6 默认开启 Thinking 模式：模型先在 `<think>` 标签内部输出推理过程，再给出最终答案。

**显存陷阱：**
- Thinking 过程的每个字也都是 token，同样占用 KV Cache
- 一个复杂问题可能 Thinking 就生成 3000 token，最终答案 500 token
- 你以为上下文只用了 4000，实际已经用了 7000
- 如果开启 `preserve_thinking` 保留历史 Thinking，多轮对话后 KV Cache 会快速增长

**应对方法：**
- 简单问题关掉 Thinking（设置 `enable_thinking=False`）
- AI Agent 场景需要 Thinking，但要限制 `max-model-len` 和并发数

## 8. 推荐配置（单卡 A800 80GB）

### Qwen3.6-27B-FP8（推荐主力）

```bash
--max-model-len 65536 \
--max-num-seqs 3 \
--gpu-memory-utilization 0.90
```

| 配置 | 权重 | KV Cache | 总占用 | 剩余显存 |
|------|------|----------|--------|---------|
| 27B-FP8 + 64K + 3 并发 | ~32GB | ~25GB | ~57GB | ~23GB |

### 35B-A3B-FP8（不推荐做主力）

- 权重更大：~35GB
- 单次推理快，但复杂代码任务质量不如 27B
- 适合场景：高并发简单问答、知识检索

---

## 9. 为什么 27B Dense 适合系统编程场景

你的场景：开发 RISC-V 内核和系统级代码 + AI Agent

| 需求 | 27B Dense | 35B-A3B MoE |
|------|-----------|-------------|
| 跨模块全局理解 | 全部参数参与推理，能整合全局信息 | 路由选择专家，跨领域容易出错 |
| 深度逻辑推理 | 全参数计算，逻辑链条连续深入 | 局部参数推理，长链条容易断 |
| 修复复杂 bug | 能追踪跨文件依赖 | 容易"脑子不够用" |

结论：对于系统编程，27B Dense > 35B-A3B MoE。

## 经验公式汇总

```
总显存占用 = 权重(固定) + KV Cache(可变) + 运行开销
并发上限 = (可用显存 - 权重 - 开销) / 单请求 KV 大小

Qwen3-27B FP8 单请求 KV 大小：
= 2 × 层数 × KV头数 × 头维度 × 序列长度 × 1 字节
= 2 × 64 × 4 × 256 × 序列长度 ≈ 128KB × 序列长度

简化估算：
- 32K 上下文 ≈ 4GB
- 64K 上下文 ≈ 8GB
- 128K 上下文 ≈ 16GB
```
