# Scoped Recovery：给 LLM Agent 工作流加上"局部撤销 + 智能重试"

---

## 0. 我们在解决什么问题

Paper 1 的 Zombie Detector 发现一个 Turn 卡死了，于是把它 kill 掉、标记为"可重试"。**但"可重试"的默认含义是从头重跑**——前面做了 7 步，死在第 8 步，那 7 步的 token 全白花了。

这在 Paper 1 的 Budget Governor 管辖下会被放大：10 个并发 agent，每个因全量重启浪费 50% 的 token，系统的有效吞吐直接减半——不是资源不够，是恢复策略太蠢。

现有框架遇到失败只有三条路，没一条够好：

| 策略 | 问题 |
|---|---|
| **盲重试**（用相同输入再跑一遍） | 失败原因没变，必然还会失败 |
| **全量重启**（从第 1 步重跑） | 前面 N 步的 token 全部浪费 |
| **人工介入** | 不可扩展 |

**核心观察：LLM 的失败通常是局部的，而且 LLM 能理解自己为什么失败。**

- 多数失败——工具参数写错、输出格式不对、工具暂时不可用——只涉及当前这一步，不波及整个任务。
- 如果把错误信息和当前进度一起给 LLM，它往往能修正参数、换个工具、调整策略重新来过——传统程序做不到这个。

所以问题变成：**怎么让 agent 在失败时只回退到最近的"安全点"，而不是回到起点？**

---

## 1. 核心思路：三个配合的机制

```
失败发生
    │
    ▼
① 在哪一层失败？            → 分层执行模型（把任务分层，每层是独立的错误边界）
    │
    ▼
② 这一层的进度保存了吗？     → 语义检查点（在每层边界生成结构化快照）
    │
    ▼
③ 能在这一层修复吗？         → 反射式局部恢复（把错误信息 + 检查点喂给 LLM，让它自己修正）
    │
    ├─ 能修复 → 继续跑，不丢前面的进度
    └─ 修不了 → 升级到上一层（而不是直接从头）
```

---

## 2. 机制详解

### 2.1 分层执行模型

把任务分成三层，每层是独立的错误边界：

```
Goal: "帮用户重构这个 Python 模块"
│
├─ 子任务层（Plan Layer）
│  ├─ 子任务 1: 分析现有代码结构
│  ├─ 子任务 2: 设计重构方案
│  └─ 子任务 3: 逐函数重构并测试
│       │
│       └─ 原子操作层（Action Layer）
│          ├─ Action 3.1: read_file("module.py")
│          ├─ Action 3.2: rewrite_function("parse_input")
│          ├─ Action 3.3: run_tests()          ← 失败
│          └─ Action 3.4: rewrite_function("format_output")
```

Action 3.3 测试失败时：
1. **先在 Action 层修**：修改 3.2 的重构逻辑，重跑 3.3。
2. **Action 层修不了**（比如设计方案本身有问题）：升级到子任务层，修改子任务 2 的方案。
3. **不需要重做子任务 1**（代码分析已经有结果了，有检查点保存着）。

**分层原则**：粒度不是固定的，而是跟着任务结构走。有自然分层结构的任务（多步工具调用、规划-执行型任务）收益大；单轮问答退化为扁平执行，本文机制不提供额外收益。

### 2.2 语义检查点

在每层边界生成结构化的进度快照——只保存结论、决策和产物引用，**不保存完整推理链**。

```json
{
  "completed": "代码结构分析",
  "key_findings": "模块有 3 个公开函数、2 个内部函数、循环依赖于 utils.py",
  "decisions_made": "决定先解耦循环依赖再重构各函数",
  "artifacts": ["dependency_graph.json"]
}
```

**与 Paper 1 的关系**：这直接复用 Paper 1 的 archive engine（`archive(turn_id)` / `resume(archive_id)` 接口），触发逻辑不同：
- Paper 1 的语义存档：被高优先级 Turn 抢占时，保存"让位前的现场"
- Paper 2 的语义检查点：在正常执行过程中主动打点，为后续恢复准备"返回点"

底层是同一个 archive 机制，上层是不同的触发条件。

**成本**：检查点只保存摘要，比全量 context 保存便宜得多。但它是有损压缩——恢复后的 context 不等于原始 context。推理链越深（>10 步连续推理），有损程度越明显，这是需要实验量化的。

### 2.3 反射式局部恢复

某个 action 失败时，生成一个恢复 prompt，把错误信息和进度上下文一起给 LLM：

```
你正在执行任务：[从检查点恢复的目标和进度]
Step X 失败了，错误信息：[具体报错]
请分析失败原因，修正你的方案，然后继续执行。
```

这不是盲重试——LLM 拿到了错误信息，可以换工具、改参数、调整策略。

**预算感知**：恢复尝试受 Paper 1 的 Budget Governor 约束。如果当前作用域内剩余预算不够一次恢复尝试，直接升级到上层作用域或 graceful fail，不做无谓挣扎。这保证了恢复过程有确定性上限，不会无限重试烧钱。

## 3. 分阶段实现

### Phase 1：基础检查点 + 局部恢复

**做什么**：
- 在 Paper 1 的 archive engine 之上实现 `checkpoint(scope_id, payload)` 接口
- 实现最简单的分层执行（两层：子任务层 + 原子操作层）
- 实现反射式恢复 prompt 生成逻辑
- 恢复失败时升级到上层或 graceful fail

**验收**：
- 注入一个会在第 5 步失败的多步任务
- 有检查点：从第 4 步的快照恢复，不重做 1–4 步
- 无检查点：全量重启（对照组）
- events 里能看到 `checkpoint_saved`、`recovery_attempted`、`recovery_succeeded/failed` 事件

**前置依赖**：Paper 1 Phase 6（archive/resume 接口）必须先完成。

### Phase 2：外置轨迹 + 基于文件的上下文检索

**做什么**：
- 把对话与关键 tool 调用轨迹持久化到文件（按 session/task 分文件）
- 恢复时拼装 prompt 时，从文件做"列目录 → 按关键词搜索 → 精读片段"式检索，而不是把整条历史塞回去
- 检查点的 `artifacts` 字段与文件检索衔接：先定位文件，再读相关段

**解决的问题**：context 触顶时，仅靠检查点摘要可能丢失可操作细节（比如某个函数的具体签名、某条 SQL 的精确写法）；文件检索补充"精确位置"，而不是用向量相似度猜。

**验收**：
- 长上下文任务（>20 步）：恢复时使用文件检索 vs. 仅用检查点摘要，后续步骤成功率对比
- 恢复 prompt 的 token 数：文件检索（精读片段）vs. 全量历史（塞回去），成本对比

## 4. 边界与限制

**恢复不是万能的**：失败原因是任务超出模型能力（比如要解一个模型解不了的数学问题），无论重试几次都不成功。本文只处理"可修正的失败"（参数错误、工具暂时不可用、输出格式错误），不处理能力边界。

**检查点有损**：恢复后的 context 不等于原始 context。推理链越深，有损越明显。这个衰减曲线是 RQ3 要量化的。

**恢复本身烧钱**：生成恢复 prompt + LLM 推理 = 额外 token。失败频率高时，恢复开销可能超过全量重启。存在盈亏平衡点，需要实验确定（这是 RQ4）。

**外置轨迹有存储与隐私成本**：落盘会话数据会增加存储负担，在有合规要求的场景下需要额外处理。这是 Phase 2 需要工程上考虑的，不是让不让做的问题。

## 5. 实验设计

### RQ1：Token 效率

在多步 agent benchmark（SWE-bench、HumanEval multi-step）上，三种策略对比：

| 策略 | 说明 |
|---|---|
| `blind_retry` | 失败后用相同输入重试同一步 |
| `flat_restart` | 失败后从第 1 步重跑 |
| `scoped_recovery` | 从最近检查点恢复 + 反射式修正 |

**指标**：每成功完成一个任务消耗多少 token？

**预期**：多步工具调用任务，scoped recovery 显著省 token；单步任务无差异。

### RQ2：局部恢复成功率

当 action 失败时，反射式局部恢复的成功率是多少？按失败类型分类：

| 失败类型 | 预期 |
|---|---|
| 工具参数错误 | 局部恢复有效（LLM 能看到参数问题） |
| 输出格式错误 | 局部恢复有效 |
| 工具暂时不可用 | 需要等待或换工具，局部恢复可能有效 |
| 逻辑错误 | 可能需要升级到上层 |
| 能力边界 | 局部恢复无效，应直接 graceful fail |

**指标**：分类成功率；升级触发率；graceful fail 触发率。

### RQ3：检查点保真度

从语义检查点恢复 vs. 从完整 context 恢复，后续步骤的成功率差多少？

在不同检查点深度下（5 步、10 步、20 步后生成的检查点），保真度如何衰减？

**这是本文的核心实验之一。** 如果保真度下降太快，结论是"语义检查点在深度推理任务上不可行"——这本身也是有价值的结论，为后续工作划定边界。

### RQ4：最优粒度

错误边界设在什么粒度最有效？

- **过细**（每个 tool call 一个检查点）：检查点 token 开销大，但恢复时丢失进度少
- **过粗**（整个任务一个检查点）：退化为全量重启

实验测量不同粒度的 cost/benefit 曲线，给出推荐的粒度选择策略。

## 6. Paper 1 与 Paper 2 的层次关系

### 两篇文章在不同层面工作，不重复

| | Paper 1 | Paper 2 |
|---|---|---|
| **操作单位** | Turn（一次 `llm.call()`） | Workflow（一个任务的多步执行序列） |
| **解决什么** | 多并发 agent 的资源治理与调度 | 单任务内部的故障恢复与进度保留 |
| **时间视角** | 横向：同时管多个 Turn 的资源竞争 | 纵向：管一个任务从开始到结束的执行过程 |

Paper 1 看到的世界是"现在有多少个 Turn 在跑、在排队、在烧钱"，它不关心每个 Turn 内部有几个步骤、哪一步失败了。Paper 2 看到的世界是"这个任务执行到第几步了、哪步出错了、怎么接着跑"，它不关心外面同时跑着几个其他任务。

### 共享基础设施，不是重复

两篇都用到"语义存档"这套机制，但用途完全不同：
- **Paper 1**：Turn 被高优任务抢占时，存一份"让位前的现场"，让它之后能续跑
- **Paper 2**：任务每完成一个子任务，主动存一份"已完成进度"，让它失败后能从这里恢复

底层是同一个 archive engine（`archive / resume` 接口），触发条件不同、使用语义不同。

### 协同增益

Paper 1 的 Zombie Detector 发现一个 Turn 卡死 → 触发 kill。
- 没有 Paper 2：kill 后全量重启，前面所有进度丢失
- 有了 Paper 2：kill 后从最近检查点恢复，只重做出错的那一步

Paper 1 的 Budget Governor 给 Paper 2 的恢复尝试划硬红线：预算不够就 graceful fail，不无限重试。

Paper 2 反过来提升 Paper 1 的资源效率：恢复成功 = 少浪费 token，Governor 看到的全局吞吐因此提升。

### archive engine 是一个被复用的基础原语

这和 Linux 的 trap mechanism 是同一个设计原则：`trap` 这一套 dispatch 机制被 syscall、page fault、硬件中断、debug 断点复用，触发条件完全不同，机制本身只有一套。Paper 1 的 archive engine 就是这个角色：

| 复用场景 | 触发条件 | 语义 |
|---|---|---|
| Paper 1 语义存档抢占 | Turn 被高优先级任务抢占 | 保存"让位前的现场"，让它之后能续跑 |
| Paper 2 语义检查点 | 子任务边界正常完成 | 保存"已完成的进度"，让失败后能从这里恢复 |

同一个 `archive(id, payload)` / `resume(archive_id)` 接口，两种完全不同的上层语义。这不是耦合，是机制与策略分离的体现——值得在论文里作为设计决策显式陈述。

实现顺序上，Paper 2 Phase 1 需要 Paper 1 Phase 6 先完成（archive engine 要先有），这是自然的层次依赖，不是设计缺陷。

### Paper 2 依赖 Paper 1 的哪些接口

| Paper 1 接口 | Paper 2 用法 |
|---|---|
| `archive(turn_id)` | 在子任务边界生成语义检查点 |
| `resume(archive_id)` | 从检查点恢复并继续执行 |
| Budget Governor `remaining_budget` | 恢复尝试前检查预算，不够就升级或 fail |
| `events.jsonl` | 写入 `checkpoint_saved / recovery_attempted / recovery_succeeded / recovery_failed` 事件 |

### Paper 1 的 Turn 状态流需要扩展

Paper 1 当前的异常状态是 `failed` 和 `zombie_reaped`。Paper 2 需要增加：

```
zombie_reaped → recovery_attempted → recovery_succeeded（→ running → completed）
                                   → recovery_failed（→ 升级到上层 or failed）
```
