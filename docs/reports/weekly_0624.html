BudgetFlow 周报

(0) Claim 1 与论文边界

Claim 1：在一个共享硬预算下，BudgetFlow 最大化 normalized verified resolved value，也就是 Yield。 BudgetFlow 的价值是：它把“模型路由”从单次请求的省钱问题，提升成一批任务共享硬预算时的价值分配问题。核心不是永远选便宜模型，也不是永远选强模型，而是在预算会耗尽的情况下，把强模型机会和预算花到更高价值、更可能产出 verified result 的任务上。

这篇论文真正要证明的是：在同一个 shared cap 下，value-aware allocation 可以比 pure T2 / pure T3 baseline 产生更高的 verified Yield，并且这个过程是可解释、可审计、可复现的。

为什么不是普通 routing

模型路由已经工业化。BudgetFlow 关心的是一批任务共用一个预算时，怎样按任务价值分配模型机会，并用 verified outcome 结算。

如何泛化

泛化性来自接口：ValueSource、Task Effort、Model Catalog、Budget Cap、Verifier 都可替换。SWE-bench 是当前压力测试，不是机制边界。

冷启动怎么做

业务方可以注入任务价值；Budget Compiler 可以按任务元数据拆预算。关键是运行前冻结价值和规则，运行后只做审计。

模块它做什么它不做什么
Budget Compiler 运行前用任务价值、估计工作量、模型价格表和历史校准数据，估算这批任务需要多紧的总预算。 它只给 shared cap，不给每个任务指定 T2 或 T3，也不预测精确花费。
BudgetFlow 运行时判断“上 T3 是否划算”：任务价值 × T3 相比 T2 的预期成功提升 ÷ 额外成本。预算越紧，选 T3 的门槛越高。 它不回写价值标签，也不重写预算规则。
两者的边界 一个负责先定预算框架，一个负责在框架内花钱。 这样可以避免循环论证，也让审计更清楚。

(0.1) Related Work 快速定位

一句话：别人多在做 per-query / per-run routing；我们做 shared-budget 下的 value allocation。 核心机制是 Value-Aware allocation + Budget Compiler。 Budget Compiler 负责运行前定预算框架，BudgetFlow 负责运行时在框架内分配模型机会。

Work / Year它们做什么缺口我们的点
FrugalGPT (2023), RouteLLM (2024), HybridLLM / AutoMix (2024), UCCI (2026), RouteNLP (2026) 每个 query 选便宜模型还是强模型。 没有 batch-level hard cap，也没有预注册 task value。 Value-Aware：先冻结任务价值，再决定预算花在哪里。
Predictive Scheduling (ICML 2025), e1 / BRPO / BudgetThinker (2025) 控制单次推理的 token/compute budget。 预算是 per-example，不是多个任务共享。 Budget Compiler：把 shared cap 编译成可审计的 batch plan。
INTENT (ICML 2025), BATS (2025), AVA (TMLR 2026), BCAS (2026) 让单个 agent run 感知工具、token 或金钱预算。 更像 Claim 2 机制，不是 Claim 1 的跨任务分配。 我们先钉死 Claim 1：同一预算下是否比 pure T2/T3 产生更多 Yield。
Topaz (CHI 2026 HCXAI Workshop), AgentServe (2026) 解释性 routing 或 serving 资源控制。 没有把 task value、shared cap、verified Yield 绑成一个主实验。 Mechanism 可审计：价值、成本、compiler、policy、verifier 分开检查。
OpenRouter 等工业界模型路由平台 在线请求级模型选择和 provider fallback。 说明 routing 有工业价值，但不是 batch-level 科研评估。 我们不是 claim “会 routing”，而是 claim “shared budget 下能多产出 verified value”。
可发表性定位：不要争“routing novelty”。要争的是： shared hard budget + task value + Budget Compiler + verified Yield。这个组合现有工作没有正面回答。

Claim 2 Future Work

Future Work为什么先不放进 Claim 1
Segment-level routing / per-turn escalation会引入切换噪声和 cache 损失；当前只做 task-start allocation。
Stop-loss / no-progress guard可能有用，但要证明不会误杀 T2 可解任务。
Cost / Routing / Escalation Memory需要 clean current-schema evidence，不能拿历史 forensic 数据当 runtime truth。
企业 AgentOS run用于验证泛化性：证明 value registration 和 compiler 是通用操作界面。
审稿人攻击点我们的防线边界
“你们是不是过拟合 SWE-bench？” 报告三类 sensitivity：等权价值、当前价值、更宽价值梯度；再加 KV 与 budget cap。指标只看冻结任务集上的 verified Yield 和 Yield / Dollar。 目前仍只验证了 SWE-bench 30-task batch；其他任务域需要后续 run。
“任务价值是不是自说自话？” ValueSource 必须预注册；主表给 current value，同时给 equal-value sensitivity，说明结论不是只靠人工权重。 真实企业价值应来自 SLA、收入影响、客户优先级；当前是研究用 proxy。
“是不是循环论证：先知道谁能过再路由？” BudgetFlow 运行时只看预注册 value、task metadata、catalog/预算规则，不使用 oracle pass/fail；oracle 只用于事后诊断。 当前第三阶段没有打出理想优势，后续还需要跑出更完美的一把过结果。

(1) 实验问题：我们到底在比什么

本轮主问题不是“哪个模型最强”，而是：在同一 30-task batch、同一 shared hard cap $6.00、同一 ValueSource/CostSource 下， BudgetFlow 是否比两个 uniform-tier baseline 更会把预算变成 verified value？

Policy角色它代表的 baseline/value
pure T2 baseline 所有任务固定用 T2 检验“弱/便宜 tier 靠更多尝试是否更划算”。这也是 BudgetFlow 选择 T2 时必须打赢的下界。
pure T3 baseline 所有任务固定用 T3 最强 uniform-tier baseline。若 T3 又强又省，BudgetFlow 必须承认并吸收这个 frontier。
BudgetFlow task-level 每个任务开始前按价值、预算压力和 task metadata 选择 tier 检验 Claim 1：共享硬预算下，value-aware allocation 能否最大化 normalized verified resolved value。
数据边界：当前 3×30 总表已经显示 BudgetFlow 赢 Yield 和 Yield / Dollar。 但第三阶段单独看没有打出理想优势，说明策略稳定性还需要更完美的一把过结果来巩固。

(2) 工业界对照：OpenRouter 已有路由，论文还剩什么价值

OpenRouter 这类工业界模型路由平台的机制很直接：它在请求级别按 prompt、供应商状态、价格、延迟和 fallback 规则来选模型或供应商，目标是让单次请求更稳、更快或更便宜。

OpenRouter / industrial routingBudgetFlow paper
请求级产品优化：统一 API、provider routing、fallback、价格/延迟/吞吐/可用性排序；Auto Router 可按 prompt 选择模型，并提供 cost-quality tradeoff。 研究级 allocation problem：固定任务 batch、共享硬预算、预注册 task value、verified task outcome，并和 pure T2/T3 baseline 计算 Yield 与 Yield / Dollar。
目标是让单次请求更可靠、更便宜或更快；失败时换 provider 或 fallback model。 目标是在预算不足时决定哪些任务值得花强模型机会，哪些任务接受弱模型或停止，最后最大化总 verified value。
产品可以说明“模型路由已经有市场价值”，但通常不提供冻结任务集、冻结价值函数、强 baseline、可复现实验和机制边界。 论文价值在于把工业直觉形式化成可审计的 shared-budget evaluation：不是 claim “路由有用”，而是 claim “在 hard cap 下 value-aware routing 比 uniform-tier baseline 更会转化预算”。

Sources: Auto Router / Provider Selection / Model Fallbacks / Model Routing overview.

Justification：工业界已经证明“模型路由”很重要，因此我们不能把 novelty 放在普通 routing 上。 BudgetFlow 的 novelty 是 shared hard budget + value registration + verified outcome accounting。 Budget Compiler 先把总预算编译成批量任务的预算框架，BudgetFlow 再在运行时决定预算怎么花。 工业系统解决在线请求分发；本文解决批量任务资源分配和可审计评估，两者相邻但不是同一个研究问题。

(3) 风险与解释

问题现在怎么解释论文里怎么写
T3 有时更便宜，是否推翻论文？ 不推翻。token 单价不等于任务总成本；T3 turn-efficient，T2 长回合会更贵。 不要写“强模型总是昂贵”；写 heterogeneous task-model fit。
BudgetFlow 花满预算是否难解释？ 它的目标不是省钱，而是在 hard cap 内最大化 verified value。主表里 BF 用满 $6.00，但 Yield / Dollar 仍高于 T3。 Claim 1 写成 fixed shared-budget value maximization，不写 unlimited throughput claim。
第三阶段没有单独打赢，是否削弱结论？ 削弱稳定性，不推翻总表。当前 3×30 总体上 BF 同时赢 Yield 和 Yield / Dollar，但 stage-level 方差说明策略还不够稳。 论文主表写 3×30 aggregate；讨论部分承认 stage-level stability 需要更完美的后续 run。
